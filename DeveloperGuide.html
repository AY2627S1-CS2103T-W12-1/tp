Developer Guide

Value proposition

TrackCall helps a membership secretary keep a club roster accurate using short typed commands. The intended MVP supports overlapping groups without repetitive edits to each record.

The secretary can:

  • Find members by name or email and narrow the displayed group by tag.
  • Add or remove a tag for the whole displayed group in one operation.
  • Keep unrelated tags and hidden members unchanged.
  • Save valid changes automatically to a local file.
  • Complete the core workflow without an internet connection or a separate save command.

This guide describes the v1.5 release candidate, which has not yet been published. It supports individual member management, name and email search, tag filtering, bulk tag editing, offline command help, local saving, CSV import/export, and name sorting. See Limitations for constraints in the current release.

Architecture

The architecture diagram shows the main components and their dependencies.

Main components

Main manages startup and shutdown through two classes: Main and MainApp.

  • At startup, it acquires the application-instance lock, initialises preferences and components, then loads or recovers the roster before opening the main window.
  • At shutdown, it stops the components and runs their cleanup methods.
Component Responsibility
UI Display the interface and receive user input.
Logic Parse and execute commands.
Model Hold the app's data in memory.
Storage Read and write data on disk.
Commons Provide classes shared by multiple components.

Component interactions

The sequence diagram shows how the components handle delete 1 and the yes that confirms it.

Each of the four main components defines an API through an interface with the component's name. A corresponding manager class implements that interface. For example, Logic.java defines the API and LogicManager.java implements it.

Components communicate through these interfaces. This reduces their dependence on each other's implementation details, as shown below.

UI component

API: Ui.java

The diagram includes MemberDetailsPanel beside PersonListPanel.

MainWindow contains CommandBox, ResultDisplay, PersonListPanel, MemberDetailsPanel, and StatusBarFooter. These classes inherit from UiPart, which provides behaviour shared by visible interface parts. HelpWindow builds its command cards from CommandHelp in the Logic component. MainWindow uses WindowPlacement to restore the saved window size and position. RosterRecoveryDialog is a JavaFX Alert that MainApp shows when the saved roster cannot be loaded. It shows the message of the DataLoadingException cause, so the user knows what to fix in the file.

The interface uses JavaFX. Matching .fxml files in src/main/resources/view define the layouts. For example, MainWindow.fxml defines the layout of MainWindow.

The UI component:

  • Holds a reference to Logic and uses it to execute commands.
  • Observes model data so the interface updates when the data changes.
  • Uses model classes, including Person, to display member details.

Logic component

API: Logic.java

The following sequence diagram illustrates parsing and executing delete 1 to request confirmation.

The sequence shows a valid index. Temporary parser objects are left to Java garbage collection, not explicitly destroyed. Result construction and other small internal operations are abbreviated.

Command execution

  1. AddressBookParser selects the matching parser, such as DeleteCommandParser.
  2. That parser produces a Command subclass, such as DeleteCommand.
  3. LogicManager executes the command. The command interacts with Model as needed.
  4. Logic returns a CommandResult containing the result.

The diagram groups model interactions into one step for clarity. An implementation may need several calls to complete that step.

Deletion confirmation

This trace shows the next input yes and a successful save. Cancellation and failures follow the policies below.

delete INDEX deletes only after the user confirms it with the next input:

  1. DeleteCommand checks the index and returns a CommandResult naming the member and their tags. The result also carries a ConfirmDeleteCommand for that Person. DeleteCommand#isReadOnly() returns true, so this step neither changes nor saves the roster.
  2. LogicManager stores the pending ConfirmDeleteCommand. While one is pending, Logic#isAwaitingConfirmation() returns true. MainWindow then highlights the CommandBox and shows a confirmation hint. If a filter box is removed before the user answers, MainWindow shows the prompt again below the filter message, so the member to be deleted stays visible.
  3. The next input does not reach AddressBookParser. If it is exactly yes after surrounding whitespace is ignored, LogicManager executes the ConfirmDeleteCommand and saves the roster as for other data-changing commands. A near miss (y, or yes in another letter case, checked by Confirmation#isNearMiss) keeps the deletion pending and reminds the user to type yes exactly. The reminder repeats the original prompt, and MainWindow keeps that prompt for later filter-box removals. Any other input cancels the deletion and is not run as a command; when it starts with a command word, the cancellation says that command was not run. Except for a near miss, the pending deletion is cleared.

ConfirmDeleteCommand stores the member rather than the index. A filter removed while the prompt is shown therefore cannot redirect the deletion to a different member. yes without a pending confirmation is an unknown command.

Alternatives considered:

  • A pop-up dialog: clearer for mouse users, but it interrupts typing, and a modal dialog would block the UI tests that drive MainWindow.
  • Running the cancelling input as a command: saves retyping, but a reply such as n would then be reported as an unknown command instead of a cancellation.

Parsing classes

AddressBookParser creates a command-specific parser, represented here as XYZCommandParser. For example, AddCommandParser uses the helper classes to create an AddCommand. AddressBookParser returns the result as a Command. AddCommandParser and EditCommandParser use PrefixValidator to reject unsupported field prefixes. TagCommandParser, UntagCommandParser, TagAllCommandParser, UntagAllCommandParser, and RenameTagCommandParser use BulkTagArgumentParser to check tag values.

Command-specific parsers implement the shared Parser interface. This allows common handling where appropriate, including in tests.

Model component

API: Model.java

Person holds references to immutable contact values and tags. Edits can reuse those objects, so the diagram uses associations rather than exclusive composition for these fields.

The Model component stores:

  • Member data: Person objects held in a UniquePersonList.
  • Displayed data: a filtered list, such as name-search results or an index selection. A SortedList wraps it for optional name sorting while the stored roster keeps its original order. An unmodifiable ObservableList<Person> lets the UI observe changes and update its display.
  • Removable filters: ModelManager keeps ActiveFilter objects for name, email, tag, and show conditions in application order. Each show condition wraps one PersonSelectionPredicate, so the UI can display and remove its box independently. Other internal predicates remain in additionalFilters. list and a successful import or clear remove the conditions. The roster heading follows the observable displayed-list size, including zero-result views.
  • Preferences: a UserPrefs object, currently containing GUI settings. Other components access it through ReadOnlyUserPrefs.

Model does not depend on UI, Logic, or Storage. Its data entities can be used independently of those components.

ModelManager#getFilteredPersonList() exposes the SortedList backed by the FilteredList. show resolves indexes against the current sorted view and adds a selection predicate to narrow it. list clears the search, tag, and selection predicates and disables sorting, restoring every member in stored order.

Alternative design: AddressBook could keep one shared Tag object for each unique tag. Each Person would reference those shared objects instead of holding its own copies.

Storage component

API: Storage.java

Storage reads and writes member data and preferences as JSON. StorageManager delegates file access to JsonAddressBookStorage and JsonUserPrefsStorage, one class per file. It depends on model classes because it saves and restores model objects. ImportCommand and ExportCommand use the CSV classes directly, not through StorageManager. CsvAddressBookCsv holds the CSV header and format shared by the importer and exporter.

CSV export is implemented as a separate CsvAddressBookExporter in the storage package. ExportCommand supplies a snapshot of the currently displayed members, in displayed order, and the destination path; the exporter writes a UTF-8 CSV file with a header row and one row per member. Apache Commons CSV handles RFC 4180 quoting and escaping. This export is a user-requested copy and does not replace or modify the JSON file used for automatic persistence.

LogicManager supplies the active roster and preferences paths to ExportCommand, which rejects destinations matching those files, their backups and recovery copies, the running JAR, or .trackcall.lock, including existing file aliases. Reserved path spellings are compared without case on every platform, including parent directories and files that do not exist yet. This intentionally also reserves case variants on case-sensitive filesystems, giving exports the same portable safety rule. CsvAddressBookExporter writes and closes a sibling temporary file before FileUtil#writeAtomically replaces the destination. A failed export preserves the previous destination and removes its temporary file; the destination's parent directory must already exist.

Offline command help

Catalogue and command flow

CommandHelp stores the nineteen implemented commands in one local catalogue. Each entry contains its purpose, syntax, example, expected result, and common errors. Only executable commands appear, so planned commands are never shown as available.

  1. HelpCommandParser accepts zero or one lowercase topic. It rejects unknown or multiple topics.
  2. HelpCommand returns the topic through CommandResult.
  3. MainWindow passes the topic to HelpWindow.

Help navigation

The overview groups commands into four category cards. Each command shows a purpose, runnable example, and button for its details. The layout uses two columns in a wide window and one in a narrow window.

  • help COMMAND opens the same detail card as its overview button.
  • All commands returns to the overview.
  • F1 and the Help menu open the overview.
  • Arrow and page keys scroll. Home/End move to the ends, and Escape closes help.

Test coverage

  • CommandHelpTest checks catalogue completeness and executable examples.
  • HelpWindowTest checks the overview, detail pages, responsive columns, navigation, and keyboard scrolling.
  • MainWindowTest exercises help add, F1, Escape, exit, rejected /help, and failed-save recovery. It uses the real command box with temporary storage.

List and clear commands

List behaviour

ListCommand resets the model predicate to PREDICATE_SHOW_ALL_PERSONS, disables name sorting, and reports the complete count using singular, plural, or empty-roster wording. LogicManager returns its result without invoking storage. Extra arguments are rejected by AddressBookParser before either the view or data changes.

Compact roster cards show member numbers, names, and tags. The details panel reveals contact fields for only the selected member. LightTheme.css provides the beige main-list palette. See Offline command help for the bundled guide.

Clear and save recovery

For a non-empty roster, LogicManager stores ClearCommand as the pending confirmation and returns a prompt with the total stored-member count. It does not execute the command or save yet. The next input consumes the pending confirmation: stripped yes executes it; a near miss (y, or yes in another letter case) keeps it pending with a reminder; every other input cancels without being parsed as a command. An already-empty roster skips the prompt.

Before executing the confirmed ClearCommand, LogicManager snapshots the roster. The command counts and removes all records while retaining the old predicate temporarily. After saving succeeds, the logic layer resets the predicate to show all and returns the success message. On an IOException, it restores the snapshot; retaining the original predicate restores the previous displayed view, including an empty search result. Settings are never changed. An already-empty clear still saves.

To meet clear's previous-file preservation requirement, FileUtil#writeToFile writes UTF-8 to a sibling temporary file and atomically replaces the destination. JsonAddressBookStorage no longer pre-creates an empty destination. Unsupported atomic replacement produces a handled failure; there is no unsafe partial-write fallback. This shared storage helper also benefits existing callers; their command policies and load validation are described below.

Readable member details and feedback

Member rows and results

Messages#format(Person) formats names, phone numbers, email addresses, addresses, and sorted tags as labelled lines for command results. MainWindow removes contact-field lines from successful add, edit, and delete feedback before showing it. UntagCommand formats its result directly as the member's name and sorted remaining tags, omitting contact fields. The roster's PersonCard displays only the member number, name, and tags. MemberDetailsPanel reveals one selected member's contact fields and provides copy buttons. Running any command clears the selection before the roster can change; F2 focuses the list and Escape hides the details. ResultDisplay wraps and scrolls text, and the split panes let the user resize the feedback and roster areas.

LightTheme.css supplies the beige palette and dark text for the main window, help, and alerts. HelpWindow.css adds the help-card layout. A welcome message points to help and help add.

Find feedback reports 1 member listed. or N members listed., including 0 members listed. List and clear use the exact count messages above. Data-changing feedback is shown only after saving. Duplicate errors state that a member with these contact details already exists and suggest edit.

Window placement

MainWindow uses WindowPlacement to check saved bounds against available display areas at startup. It retains valid positions, selects the display with the greatest overlap or the primary display as a fallback, and brings oversized or off-screen bounds back within that display. Invalid saved dimensions also recover to usable bounds. This handles monitor changes between sessions.

Automatic data saving and load recovery

Save policy

LogicManager#execute(String) parses and executes a command, then checks Command#isReadOnly(). help, list, show, sort, find, findemail, filter, export, and exit return without saving member data. delete INDEX and a non-empty clear return without saving while awaiting confirmation. Cancellation also returns without saving. Successful add, edit, tag, untag, confirmed delete, tagall, untagall, renametag, clear, and import commands pass the complete roster, including hidden members, to Storage#saveAddressBook. Parsing and execution failures do not save. Data-changing commands return normal success only after the save succeeds.

File writes

StorageManager delegates JSON storage to JsonAddressBookStorage. The default file is data/addressbook.json, relative to the JAR folder in packaged builds or the working directory in development. FileUtil#writeToFile creates missing parent directories, writes UTF-8 to a sibling temporary file, and replaces the destination with an atomic move. It reports a failure if atomic replacement is unavailable instead of falling back to a potentially partial overwrite. An existing saved file remains intact on failure; temporary-file cleanup is attempted.

Failed saves

If saving fails, LogicManager reports a SaveFailureException, a CommandException subtype that also records whether the change remains applied.

For add, edit, tag, untag, confirmed delete, tagall, untagall, renametag, and import, the model change remains in memory. CommandBox clears the already-applied input so pressing Enter cannot accidentally repeat an indexed edit or deletion. The result explains that the previous saved roster is unchanged.

To retry, the user resolves the storage problem and checks the current list. They reapply an existing field value with edit, or use clear if the roster is empty. This saves without changing another record.

Before executing a confirmed clear, LogicManager snapshots the roster. A successful save resets the search predicate. If saving fails, it restores those records while retaining the existing search predicate, so the previous displayed list returns. The result says No members were removed. and CommandBox retains the submitted input. The user must run clear again to start a fresh confirmation; another yes alone cannot repeat the action. A failed clear of an already-empty roster also reports failure rather than the normal empty result. Exiting never retries a save. Application preferences are stored separately at startup and shutdown.

Startup and validation

MainApp#init() acquires AppInstanceLock before reading preferences or roster data. The lock is held on .trackcall.lock in the application folder for the complete session, including shutdown preference saving. A second instance is rejected with an already-running explanation. The lock is released on initialization failure or normal shutdown; the operating system also releases it when the process terminates. The lock file remains on disk and must not be deleted to start another session. The overload accepting explicit preferences/roster paths supports isolated startup tests.

Startup loads a valid roster in file order. A missing file produces sample members; a loading error requires recovery before the editable roster opens. A JSON null root, null person, and null tag are rejected through the normal loading-error path. JsonAddressBookStorage preserves the exact damaged bytes in a unique sibling .corrupt-....json file. The startup dialog offers a validated backup, an explicit empty roster, or closing without replacement. Preservation failure prevents startup. Recovery verifies that the original still matches its preserved copy and replaces the roster atomically without rotating the existing backup.

Normal saves validate the current roster. If its member list differs from the requested save, they atomically copy the previous roster to the sibling .bak file; backup failure prevents replacement, and an invalid existing roster blocks normal saves until recovery. An unchanged save still attempts to write the current roster but retains the previous distinct backup. JsonAddressBookStorage also remembers the roster it last read from or wrote to the data file. If the file now holds a different valid roster, it was changed outside TrackCall, so the first save is refused with a storage error and the change stays in memory. The refused save records the outside version, so a retry replaces it and keeps its exact bytes in .bak, even if its member values match the requested save. This backup requirement remains pending after a failed write and clears after a successful save or explicit reload. Formatting-only edits are not refused.

Design considerations for outside-edit detection: comparing the parsed roster (the current choice) ignores formatting-only edits and unchanged files, at the cost of one extra read per save. Alternatives: a modification time or hash is cheaper, but a hash flags whitespace-only edits and timestamps can be unreliable; watching the file and reloading would silently discard unsaved in-memory changes and needs platform-specific watchers. An edit that leaves the file invalid is not treated as an outside change; saves then fail until restart and recovery.

Export protects both backup and recovery filenames. Null or invalid preferences fall back to defaults, which are saved through the usual preferences setup.

The current JSON format uses a persons array and a tags array per member. Duplicate identity compares all four trimmed contact fields exactly, including case and internal spacing, and ignores tags. This legacy Person#isSamePerson rule remains the storage invariant so older rosters continue to load. For new input, Person#isDuplicateContactOf compares names with String.equalsIgnoreCase after whitespace collapse, with exact trimmed phone/email/address comparisons. This handles Unicode case pairs such as Greek sigma without context-sensitive lowercasing. Add and edit reject a match against another stored member; import skips matches against the roster and earlier accepted rows. Stored names, equals and hashCode are unchanged. Tags and unchanged-contact edits remain possible on legacy variants. The email validator avoids excessive backtracking on long input, and a log-file initialisation failure uses the console logger instead of aborting startup.

Command parsing

ArgumentTokenizer recognises the supported lowercase field prefixes when preceded by whitespace, including a tab. It trims surrounding value whitespace without removing internal address tabs or slashes. list, sort, clear, and exit reject extra arguments before execution. Invalid commands leave records, the current list, and the saved file unchanged; the input remains available for correction.

AddCommandParser and EditCommandParser use PrefixValidator to check whitespace-delimited single ASCII letters followed by / before tokenising. Only n/, p/, e/, a/, and t/ are supported. Unknown letters and uppercase prefixes report the corresponding command's usage message before field validation. The standalone c/o abbreviation (case-insensitive) is exempt; URLs, numeric slashes, and slashes embedded in words are literal text. While inside an a/ field, A/ followed by an ASCII digit is exempt too, preserving Block A/12. Supported lowercase prefixes end that address context; other unsupported prefixes still fail. Other commands retain their own parsing rules.

CSV import

ImportCommandParser accepts exactly one p/FILE_PATH parameter. It removes matching outer quotes, requires quotes around paths containing whitespace, rejects repeated or unknown prefixes, and accepts the .csv extension case-insensitively while preserving path case.

CsvAddressBookImporter rejects sources over 10 MiB, bounds the read to detect files that grow, and rejects more than 10,000 non-blank member rows before duplicate removal. It reads strict UTF-8, accepts an optional byte-order mark, checks the exact lowercase five-column header in any column order, and uses the shared Apache Commons CSV format for quoting and escaping. It rejects embedded line breaks and trims surrounding whitespace from field values and individual tags before validation. Records are parsed and validated in source order, with syntax and field errors identifying the physical row. It returns an immutable member list only after validating the whole file, so errors cannot cause a partial import. Completely blank records are skipped but still contribute to reported row numbers.

ImportCommand compares each valid candidate with the complete stored roster and earlier accepted rows using Person#isDuplicateContactOf. It appends only unique members in source order, then clears search, filter, and sort state. LogicManager performs the normal automatic save even for a header-only or duplicate-only import. If saving fails, the imported batch remains in memory. The import-specific save error is followed by the shared warning about unsaved changes, loss on exit, and retrying after storage access is restored. The source CSV is read-only throughout the workflow.

Import sequence

The sequence shows a valid file after command parsing. The importer validates the complete file before the command changes the model, so a read or validation failure cannot import a partial batch. Duplicate selection uses the complete roster, including hidden members, and earlier accepted CSV rows. The logic layer returns success only after saving, including when every row is skipped or the file contains only a header. An import-save failure leaves the imported batch in memory and preserves the previous saved roster.

CSV export

ExportCommandParser rejects double quotes in destination paths before any file is written, so exports do not produce filenames that ImportCommandParser cannot read. Spaces remain supported without surrounding quotes.

The sequence shows a successful export after command parsing. LogicManager supplies the active roster and preferences paths to ExportCommand, which checks the destination against protected application files before calling CsvAddressBookExporter. Path resolution also applies the shared file-location restrictions. The command snapshots model.getFilteredPersonList() and exports only those members in displayed order, including active sorting. It counts hidden members against the complete roster and reports both counts when any are excluded. With everyone visible, existing success feedback is retained. An empty displayed list writes only the header. Run list first to export everyone in stored order.

FileUtil#writeAtomically invokes the exporter's FileWriter#write callback with a sibling temporary file. Apache Commons CSV handles quoting and escaping; the writer closes before atomic replacement. A write or replacement failure preserves the previous destination and attempts temporary-file cleanup. On success, isReadOnly() prevents the logic layer from saving the automatic JSON roster. Neither successful nor failed export changes the displayed filters or sorting.

Selecting members and sorting

show INDEX [MORE_INDEXES]... validates every index against the current displayed list before changing the view. ShowCommand stores the corresponding members in a PersonSelectionPredicate; repeated indexes collapse to one member, and argument order does not reorder the list. Each distinct show selection adds another condition, so it can only narrow the current view. ModelManager#setPerson updates these predicates after an edit or tag change to keep the selection attached to the member. Each distinct show selection has a separate box in command order. Repeating a selection with the same members leaves the existing box in place. Its label reports the number of selected members and its tooltip lists their names. Removing that box removes only its predicate, leaving the other show, name, email, and tag conditions active. ActiveFilter#getShowSelectionNames() sorts tooltip names with String.CASE_INSENSITIVE_ORDER; this does not change the displayed roster order. list, successful add, successful clear, and valid import clear the selections.

SortCommand enables a comparator on ModelManager's SortedList. It compares names ignoring case and repeated internal spaces, without modifying the stored names or roster order. Equal names retain their stored relative order. Filters and record edits preserve sorting; list and valid import disable it. Both show and sort are read-only and never save the roster.

ShowCommandParserTest, ShowCommandTest, AddressBookParserTest, and LogicManagerTest cover validation, selection narrowing, record replacement, ordering, and read-only execution.

Find members by email

findemail KEYWORD [MORE_KEYWORDS]... narrows the displayed members by their email addresses.

  • Matching: accept any whitespace-separated keyword within one command, including nonbreaking-space separators. Lowercase the email and keywords with Locale.ROOT, then match literal substrings. Full addresses and fragments such as @example.com are supported; regular expressions, names, and phone numbers are not searched.
  • Validation: reject blank input before changing the view.
  • Model update: FindEmailCommand calls ModelManager#filterFilteredPersonListByEmail. A distinct query appends a removable ActiveFilter and reapplies all active conditions using logical AND.
  • Repeated queries: ActiveFilter#hasSameSearch compares keyword sets for searches of the same kind. Name comparisons use Java's case-insensitive ordering; email comparisons use Locale.ROOT lowercase, matching their respective predicates. Keyword case, order, and repetitions are ignored; the original label is retained. Both model search operations return whether a condition was added.
  • Feedback: a repeat reports that the search is already active. A different query that leaves the displayed count unchanged reports Results unchanged. and keeps its new condition. Because searches only narrow the list, equal counts mean the same members remain visible.
  • Retained state: keep earlier name searches, email searches, tag filters, show selections, and name sorting.
  • Filter boxes: show one Email box per distinct search, in application order with name, tag, and show boxes. Its X removes only that condition. Remaining conditions still determine which members appear.
  • Edits: re-evaluate the email predicates when a member changes. A nonmatching member disappears from the view but remains stored. Edit and delete use current displayed indices.
  • Reset and storage: list restores the full roster in stored order. Email searches are read-only and do not save.

FindEmailCommandTest, LogicManagerTest, CommandSequenceOracleTest, and MainWindowTest cover cumulative searches, order-independent matching, selections, chip removal, sorting, and unchanged saved data.

Filter members by tag

filter t/TAG [t/MORE_TAGS]... narrows the displayed list to members with at least one of the given tags, ignoring letter case, without changing member data. Tags in the same command are alternatives (logical OR); separate commands narrow the list further (logical AND). Usage examples are in the User Guide.

Parsing

FilterCommandParser accepts one or more t/TAG arguments. It splits them on whitespace followed by t/, trims each value, and requires 1 to 30 characters using ASCII letters or digits with optional internal hyphens. A missing t/, an unknown prefix, or any invalid or empty tag rejects the whole command before the view changes. Each value is validated by BulkTagArgumentParser#parseTagName, the same method tagall, untagall and renametag use, so an invalid tag reports the same specific reason (unsupported character, hyphen placement, length, or empty) before any tag is added. A repeated tag, in any letter case, counts once because FilterCommand keeps its tags in a LinkedHashSet.

Execution

FilterCommand passes its tags to ModelManager#filterFilteredPersonListByTags, which adds one ActiveFilter of kind TAG whose predicate is true when a member has any of those tags (anyMatch). The model combines this filter with the active name, email, tag, and show conditions using logical AND. So filter t/a t/b followed by filter t/c means (a or b) and c. ActiveFilter#hasSameTags compares tag sets ignoring order and letter case. If an equal filter is already active, FilterCommand leaves the conditions and displayed list unchanged and reports the active filter's stored spelling followed by the current result summary. The filter box label joins alternatives with / (ActiveFilter#ALTERNATIVES_SEPARATOR), for example Tag: committee / alumni. find and findemail boxes use the same separator, for example Name: Alice / Tan and Email: @example.com / @school.edu, because keywords within one of those commands are also alternatives. The word "or" is not used as the separator because a tag can legally be named or, which would make Tag: a or or or b ambiguous; / cannot appear in a tag. ActiveFilter#getLabel caps a tag group at ActiveFilter.MAX_SHOWN_TAGS (4) tags, so a long group cannot make one box wrap across the filter area: filter t/a t/b t/c t/d t/e t/f shows Tag: a / b / c / d / +2 more. + cannot occur in a tag, so +N more is never mistaken for one. ActiveFilter#getFullLabel always lists every tag, and MainWindow uses it for the box's tooltip and the remove button's accessible text, so no information is lost. Name and email boxes are not capped; JavaFX ellipsizes an over-long label and the tooltip holds the full text. The model keeps removable name, email, tag, and show conditions in application order, shown left to right in the UI. find adds a distinct name condition and findemail adds a distinct email condition; list clears all conditions. Applying name, email, and tag conditions in a different order gives the same matching members when the roster is unchanged. The observable filtered list updates automatically, and the command reports the resulting member count and all active tag names. A single tag uses N member(s) listed with tag "TAG".; multiple tags use N member(s) listed with tags "TAG1", "TAG2". in application order. Tags that came from one command are joined with /, for example N member(s) listed with tags "TAG1" / "TAG2". A comma between conditions means AND and a slash within one means OR. To keep the two readable, FilterCommand#formatCondition puts a group in parentheses whenever more than one tag condition is listed, for example N member(s) listed with tags ("TAG1" / "TAG2"), "TAG3".; a lone group stays unparenthesized. A zero-match result is successful.

Filtering preserves the current display order, including name sorting. Visible members are renumbered, and subsequent edit and delete commands use those displayed indices. The command is read-only, so LogicManager returns its result without saving the roster.

Design considerations

  • Preserve earlier conditions: combining predicates lets users narrow an existing name search, email search, or tag filter without restoring hidden members. For example, filtering by committee and then year1 keeps members with both tags. Another find or findemail also narrows the view; list clears all conditions.
  • OR within a command, AND between commands: keywords of find and findemail already mean "any", so allowing several tags in one filter keeps the three commands consistent. Without it, a request such as "committee or alumni" could not be expressed, because successive filters can only narrow. One ActiveFilter holds the whole group, so its X removes all alternatives together. An alternative was one box per tag with an OR flag, but that makes the left-to-right box order ambiguous and the X button's effect unclear.
  • Keep filters active after edits: the model retains the predicate rather than a fixed set of matching members. Replacing an edited member in the observable list re-evaluates that predicate. A member who no longer matches disappears from view but remains in the roster, so later commands operate on the updated group.

Individual tag editing

tag INDEX t/TAG adds one tag to the member at the displayed index. untag INDEX t/TAG removes one tag from that member. Both commands use the displayed-index convention of edit and delete and the existing single-tag validation used by the bulk tag parsers.

Each command reads the member from Model#getFilteredPersonList() at execution time. It copies the member's tag set, changes only the requested tag, constructs a new Person with the original contact fields, and calls Model#setPerson. This preserves active search and tag filters, sorting, and show selection. If removing a tag causes a member to fail an active filter, the member leaves the displayed list but remains in the roster.

Adding an existing tag or removing an absent tag is a valid no-op with explicit feedback. No model replacement occurs, but LogicManager still saves the full roster. A bad or out-of-range index and invalid arguments fail before saving. A save failure after an actual change follows the standard SaveFailureException path and leaves the change in memory.

Bulk tag editing

tagall t/TAG adds one tag, and untagall t/TAG removes one tag, for every member in the displayed list.

Parsing

TagAllCommandParser and UntagAllCommandParser both delegate to BulkTagArgumentParser#parse, so the two commands share one grammar and one set of error messages. It accepts exactly one tag of 1 to 30 characters using ASCII letters or digits with optional internal hyphens. Surrounding spaces are ignored. tag and untag use the same method for their tag argument.

  • A missing t/ reports Missing t/ prefix. Supply tags using t/TAG.
  • Text before a supplied t/ is named in an Unexpected text before t/ error.
  • An n/, p/, e/, or a/ prefix is named as an unsupported field. Each of these errors includes the calling command's usage.
  • An empty tag reports Tag cannot be empty.
  • More than one t/ reports Only one tag can be applied per command. Run the command once for each tag.
  • Unsupported characters are named in the error, followed by the allowed ASCII letters, digits, and internal single hyphens. A space, tab or other whitespace inside a tag reports Tag cannot contain spaces. Use a hyphen instead, e.g. year-1. A double quote is shown escaped as \".
  • Leading, trailing, and consecutive hyphens each report a specific error with year-1 as a valid example.
  • Unsupported characters are checked before length, so non-ASCII code points are not misreported as overlong ASCII tags. Invisible control characters are shown as code points, for example U+0000.
  • Overlong tags report their actual length and the limit from Tag.MAX_LENGTH.
  • These argument errors give the reason followed by usage without a generic format-error header. Existing index parsing in tag and untag retains its format-error header.

Execution

TagAllCommand and UntagAllCommand extend the abstract BulkTagCommand, whose execute method follows the steps below. Each subclass supplies only needsUpdate, which decides whether a member changes, and updateTags, which adds or removes the tag.

  1. Copy Model#getFilteredPersonList() into a new list. This fixes the target set before any update. The copy matters because each update refreshes the displayed list. For example, removing the tag used by an active single-tag filter hides the updated member immediately. A member stays visible if they still satisfy every active condition, for example by matching another alternative in a filter t/a t/b group.
  2. Reject an empty target set with There are no members in the current list to update. Run list to show everyone, or use find or filter to choose a group.
  3. For each target that lacks the tag (tagall) or has it (untagall), build a new Person with an updated copy of its tag set and call Model#setPerson. Other targets are skipped. Hidden members are never visited.
  4. Report the changed count, and the skipped count when it is non-zero, for example Added tag "committee" to 9 member(s). 3 already had this tag (any letter case). A zero changed count adds No changes were made., for example Removed tag "committee" (any letter case) from 0 member(s). 3 did not have this tag. No changes were made. If the active filters now hide updated members, which only untagall can cause, it also reports the displayed list using TagUpdateUtil#describeHiddenUpdates, for example 0 member(s) listed with tag "committee". Run list to show everyone.

Neither command changes the search predicate or name sorting, so the current view stays applied after the batch. Tags are not part of a member's identity, so an update can never create a duplicate member.

Both commands are data-changing (isReadOnly() is false). LogicManager therefore saves the complete roster after every valid invocation, including one where every target is skipped. An empty target set throws before saving. A failed save follows the standard SaveFailureException path: the whole batch remains in memory and the previous saved file is unchanged.

untagall differs only in needsUpdate and updateTags. renametag follows the same flow through RenameTagCommandParser. Temporary parser objects are left to garbage collection, not explicitly destroyed.

Design considerations

  • One shared argument parser: keeps tagall and untagall input rules and messages identical. It and FilterCommandParser use the shared Tag model rule, which also applies to add, edit, and loading saved data.
  • Shared base class: BulkTagCommand holds the steps both commands share, so the two commands cannot drift apart in how they select targets, log results, or word their feedback.
  • Skip instead of reject: a member who already has (or lacks) the tag is skipped and counted, so one overlapping group does not block the rest of the batch (UC03 extension 6b).
  • Alternative: act on the whole roster: simpler, but it cannot target a filtered group (US09). Running list first gives whole-roster behaviour when it is wanted.
  • Alternative: an index list such as tagall 1 3 5 t/TAG: precise for small groups but error-prone for large ones. Using show first to narrow the displayed list achieves the same result.

  • TagAllCommandParserTest, UntagAllCommandParserTest, and BulkTagArgumentParserTest cover valid tags, length boundaries, missing prefixes, preambles, and empty, invalid, or repeated tags.
  • LogicManagerTest checks that only displayed members change, that no-op batches save, and that an empty list does not save.

Renaming a tag

renametag t/CURRENT_TAG t/NEW_TAG replaces one tag with another for every displayed member who has it.

RenameTagCommandParser reads the t/ values with BulkTagArgumentParser#parseTagValues and requires exactly two. A different count reports the received count and explains that the current tag precedes the new tag. Text before the first t/ and unsupported member field prefixes receive the shared specific errors, with the renametag usage. Each value is validated by BulkTagArgumentParser#parseTagName, so empty and invalid tags report the same messages as tagall and untagall. Identical spellings report The new tag must be different from the current tag. Case-only changes are allowed so a group can use one capitalization.

RenameTagCommand#execute:

  1. Collects every member in Model#getFilteredPersonList() who has the current tag. Like tagall and untagall, the target set is the displayed list, so members hidden by a search or filter are not changed.
  2. Rejects an empty target set with No member in the current list has the tag "CURRENT_TAG"., followed by how many hidden members have the tag when there are any. This throws before saving.
  3. For each target requiring a change, builds a new Person whose tag set has the current tag removed and the new tag added, then calls Model#setPerson. A target that already has a distinct new tag keeps one copy and is counted as merged. A case-only rename skips members already using the requested spelling and does not count matching tags as merges.
  4. Reports the changed count, and the merged count when it is non-zero, for example Renamed tag "year1" to "year2" for 10 member(s). 2 already had "year2". If renamed members are now hidden, it also reports the displayed list using TagUpdateUtil#describeHiddenUpdates, for example 0 member(s) listed with tag "year1". Run list to show everyone. A case-only rename that changes nobody reports Every displayed member with this tag already uses "NEW_TAG". No changes were made. Finally, if hidden members still have the current tag, it adds N hidden member(s) still have "CURRENT_TAG". Run list, then renametag again to rename it for everyone.

Like the other bulk commands, it keeps the current search, filters and sorting, and saves the complete roster through the standard data-changing path.

Design considerations

  • Displayed list instead of whole roster: all three bulk tag commands act on what the user can see, so a rename can be limited to part of a group. Running list first renames the tag for everyone (US29).
  • Reject an unused current tag: reporting 0 member(s) would hide a likely typo. Matching ignores letter case, and rejecting an unused tag also avoids an unnecessary save.
  • Allow case-only renames: tag identity ignores case, but the displayed spelling matters. Comparing the two spellings exactly allows a bulk capitalization change without creating duplicate tags.
  • Merge keeps the typed spelling: when a member already has the new tag in another letter case, that member ends up with the spelling typed in the command, so the result is predictable for the user.
  • Alternative: untagall then tagall: reuses existing commands, but removing the old tag can hide members from an active filter on it before the second step runs, and it needs two saves. Rejected.

Test coverage

RenameTagCommandTest, RenameTagCommandParserTest, and LogicManagerTest cover renaming, merging with an existing tag, hidden members that keep the current tag, unused and differently cased tags, wrong tag counts, invalid and identical tags, and whether each case saves.

Limitations

These are constraints of the current implementation:

  • The saved JSON format uses a persons array with a tags array for each member. Loading ignores unknown member fields, keeps the last value of repeated fields, and accepts JSON numbers in text fields as text. Comments and trailing commas are rejected.
  • Deletion and clearing a non-empty roster ask for confirmation. Neither has undo after confirmation. After an accidental confirmed clear, stop making changes and close TrackCall before restoring. The backup at data/addressbook.json.bak retains the previous distinct saved roster. An unchanged save preserves it, but a later save with different data replaces it. Follow the User Guide's manual recovery steps.

Product scope

Target user profile

  • A club or small organisation's membership secretary who maintains its member roster.
  • Works with names, phone numbers, email addresses, addresses, and overlapping groups such as committees, cohorts, membership tiers, and alumni. The source persona, Rachel Ng, uses the roster especially during term starts, renewals, and committee changes.
  • Can type quickly and prefers short keyboard commands to repeated form filling or mouse actions.
  • Regularly adds new members, corrects contact details, looks up members, and updates group tags.
  • Starts by trying sample records and checking results, then learns frequently used commands.
  • Uses the app on their own computer as a single operator. Shared accounts, concurrent editing, and routine shared-file access by several users are outside the product scope.
  • Needs a small local roster. The performance target is 500 members; this is not a limit that rejects a 501st record.

Value proposition: See the product value proposition at the start of this guide.

Selected MVP

The MVP includes these commands:

  • Help and session: help, exit.
  • Individual records: add, edit, delete.
  • Roster and search: list, show, find, findemail, clear, filter.
  • Individual and group tags: tag, untag, tagall, untagall, renametag.

The MVP also includes automatic saving and manual editing of the local data file. Each member has a name, phone number, email address, an optional address, and zero or more tags.

Scope boundaries

The broader narrative must be read with these MVP decisions:

  • Groups are tag assignments, not separate group objects. A label such as "Batch 2026" must be represented by a valid tag such as Batch2026; spaces are not allowed inside tags.
  • Bulk selection means everyone in the displayed list after searching, filtering, or selecting displayed indexes with show. There is no direct edit/delete-by-name command. Individual edits and deletions use the current displayed index, which the secretary must check first.
  • find matches complete or partial name words. findemail matches literal email substrings. Phone-number search is a considered idea, not current MVP search behaviour.
  • Name sorting is available through sort; list restores stored order.
  • vCard import/export, sorting by criteria other than name, archiving, bulk editing of non-tag fields, and an in-app handover/access feature are outside the selected MVP. The initial discussion also considered dedicated grade, class, membership-status, and joining-date fields. These remain future ideas; the MVP stores the contact fields and tags listed above. Cohorts, tiers, or paid/unpaid categories may be represented by tags, without calculating fees or payment status.
  • Deletion asks for confirmation and has no undo. Archiving with retained history is different from deleting a record.

Reviewing a manually edited JSON file is a separate workflow, not an implementation of import/export.

Shared behaviour rules

These rules describe the selected MVP and apply to the use cases below.

  1. Command keywords and prefixes are lowercase. Trim surrounding spaces and tabs from values. Reject invalid input before changing records, the displayed list, filters, or the saved file. Supplied non-empty field values use the same validation in add and edit. A bare a/ in edit clears the optional address; a bare a/ in add is rejected. Manual data loading also accepts an empty address value to represent an address that was not supplied.
  2. New contact input is a duplicate when names match after ignoring capitalization and collapsing whitespace, and trimmed phone, email and address match exactly. Tags are ignored. Stored names retain their original capitalization and spacing; accents and punctuation are not removed. Different people may share a name when another contact field differs. An edit excludes its own record. Older saved name variants remain loadable; tag-only and unchanged-contact edits remain available. Duplicate checking does not establish a person's real-world identity.
  3. A tag contains 1 to 30 ASCII letters or digits with optional internal hyphens and matches regardless of letter case. It contains no other whitespace. Store each tag once per member, retaining its spelling for display, and display tags in ASCII order: hyphens, digits, uppercase letters, then lowercase letters.
  4. list resets all searches and tag filters. find KEYWORD [MORE_KEYWORDS] narrows the displayed list. It matches complete or partial name words, ignores letter case, and accepts a match on any keyword within one command. Consecutive find commands retain the intersection of their matches and any active tag filters. Repeated keywords do not repeat records. findemail KEYWORD [MORE_KEYWORDS]... also narrows the displayed list. It matches literal email substrings using any whitespace-separated keyword, ignoring case. Each distinct email search adds a removable condition; all conditions must match. Neither search clears earlier conditions or disables sorting.
  5. filter t/TAG narrows the currently displayed list using case-insensitive tag matching. Repeated filters retain the intersection of the tags and active name or email searches. A valid zero-match result is successful. Use list first to filter the whole roster.
  6. An index is an ASCII-digit integer from 1 through the current displayed count. Leading zeroes are accepted; signs, decimals, and internal whitespace are not. It refers to the list when the command is submitted. Commands preserve roster order and renumber the displayed records.
  7. edit INDEX ... changes only supplied fields. At least one field must be supplied. A lone a/ clears the address. Supplied tags replace the full existing tag set. A lone t/ clears all tags and cannot be combined with a non-empty tag. Reapply the active search and filters after an edit; an edited member can disappear from the view while remaining stored. tag INDEX t/TAG adds one tag to a displayed member; untag INDEX t/TAG removes one tag. Both retain the member's other tags and contact fields. An existing or absent tag is a valid no-op that still attempts to save. Removing a tag used by a filter can hide the member.
  8. tagall t/TAG and untagall t/TAG accept exactly one tag and fix their target set to everyone displayed when the command is submitted. Hidden members and unrelated tags are unchanged. Adding an existing tag or removing an absent tag skips that member. Reapply searches and filters after the whole batch. Changed and skipped counts refer to the original target set.
  9. Valid add, edit, tag, untag, confirmed delete, clear, tagall, untagall, renametag, and import commands save the complete roster, including valid operations that make no change. An empty bulk target, or a renametag current tag that no displayed member has, is an error and does not save. help, list, show, sort, find, findemail, filter, export, and exit do not save. Neither does delete INDEX while it waits for confirmation, nor a cancelled deletion. A pending or cancelled non-empty clear does not save.
  10. Report data-changing command success only after saving succeeds. A failed save preserves the previous saved file and reports a storage error. Except for clear, changes remain in memory and can be lost on exit. Failed clear restores the previous records, displayed list, and filters. To retry saving, resolve the storage problem and run a valid data-changing command; a valid no-op can be used without making another data change.
  11. add restores the full list and appends the record. delete names one indexed record and removes it only after the next input is yes; y or another letter case of yes keeps the prompt pending with a reminder, and any other input cancels without running it. The deletion retains the active search and filters. clear removes all records, including hidden ones, resets the view, and preserves application settings. A non-empty roster requires a yes confirmation; near misses keep the prompt pending as for delete, and any other reply cancels without being run. An empty roster skips confirmation. Neither action has undo. list, sort, clear, and exit reject extra arguments. exit closes the app without a final save or another warning about unsaved changes.
  12. Startup reads the local data/addressbook.json relative to the JAR folder in packaged builds or the working directory in development. A missing file loads sample members and logs that fact. An invalid or unreadable file opens a recovery dialog before the roster can be edited. The app preserves the damaged file, then offers a valid backup, an explicit empty roster, or closing without replacement. A valid empty roster stays empty. Normal startup and read-only commands leave the roster file untouched.
  13. An unknown command, including a wrong-case keyword, reports Unknown command. Type help for available commands. An invalid known command identifies the format or field problem and provides its usage or a route to help COMMAND. A duplicate error identifies the rejected record as a duplicate; it does not merge or overwrite records. These input errors leave records, the current view, and the saved file unchanged. Storage failures are reported separately because a data change may already exist in memory (rule 10).

UC02: Find and update a member

Related stories: US03, US04, US05, US24, US25, US26, US28.

Goal: correct one member's record.

MSS

  1. The secretary searches for complete words or parts of words from the member's name.
  2. TrackCall lists matching records and their current indices.
  3. The secretary checks the contact details to identify the intended member, then submits its displayed index and the fields to change, or uses tag INDEX t/TAG / untag INDEX t/TAG to adjust one tag while retaining the rest.
  4. TrackCall validates the request, updates the record, saves the roster, and reapplies the search and filters.
  5. TrackCall reports the update with the member's name and tags. The secretary can select the member to check contact details in the details panel. The use case ends.

Extensions

  • 1a. The search has no keyword. TrackCall reports the input error and preserves the view. The secretary can retry step 1.
  • 2a. No record matches. TrackCall shows an empty result. The secretary can search again at step 1 or end the use case without changing data.
  • 4a. The index or fields are invalid, no field is supplied, or the edit duplicates another record. TrackCall reports the error without changing records or the view. The secretary can retry step 3.
  • 4b. Saving fails. The edit remains in memory, the saved file is unchanged, and TrackCall reports the storage error. The use case ends without confirmed persistence; recovery follows rule 10.

An edited member that no longer matches the search or filters disappears from the displayed list but remains in the roster. The secretary can use list to see it again.

The search command is find KEYWORD [MORE_KEYWORDS]. It accepts one or more whitespace-separated keywords, ignores case, matches complete or partial name words, and returns records matching any keyword in address-book order, or in name order while sort is active.

A successful search reports 1 member listed., N members listed., or 0 members listed. and does not save the data file. A repeat prefixes the count with This name search is already active.; a different query with unchanged results prefixes it with Results unchanged. Repeats preserve the original box, ignoring keyword case, order, and repetitions. find with no keyword reports Invalid command format. followed by the find usage; a wrong-case command such as FIND John reports Unknown command. Type help for available commands. A new find narrows the displayed list and retains previous name searches and tag filters.

Partial matching uses contiguous text within a name word: Jo, oh, and hn each match John Tan. It does not correct spelling or match across spaces. find oh Tan matches either keyword, and repeated keywords do not duplicate members. Only names are searched; contact details and tags are excluded.

findemail KEYWORD [MORE_KEYWORDS]... (US37) narrows the displayed list, retaining earlier name searches, email searches, tag filters, and show selections. It matches literal email substrings with case-insensitive OR matching within each command. Successive distinct email searches are combined with AND; each adds its own removable Email box. Repeats keep the original box and prefix the count with This email search is already active. Different queries with unchanged results retain their own boxes and prefix the count with Results unchanged. For example, findemail alice@example.com @school.edu matches either fragment. It preserves name sorting and does not save. Missing keywords report invalid command format and preserve the current view.

UC03: Update a group's tags

Related stories: US08, US09, US10.

Goal: change one group assignment without changing unrelated tags.

MSS

  1. The secretary requests the complete roster.
  2. TrackCall lists all members.
  3. The secretary searches or filters to identify the intended group.
  4. TrackCall displays the matching members.
  5. The secretary checks the affected group and requests adding or removing one tag from it.
  6. TrackCall validates the request, fixes the target set, updates its tags, and saves the roster.
  7. TrackCall reapplies the search and filters and reports changed and skipped counts. The use case ends.

Example: enter list, filter t/year1, and tagall t/committee as separate commands. This adds committee to the displayed year-one members and retains their other tags.

Extensions

  • 3a. A search or filter request is invalid. TrackCall reports the error and preserves the prior view. The secretary can correct the request at step 3.
  • 4a. No members match. The secretary can restart at step 1 or end the use case. A bulk update on an empty list is rejected without changing or saving data.
  • 6a. The tag is empty or invalid, or more than one tag or an unknown prefix is supplied. TrackCall reports the error and changes nothing. The secretary can retry step 5.
  • 6b. Some targets already have the added tag or lack the removed tag. TrackCall skips those assignments, saves the roster, and continues to step 7. A non-empty target with no changes is still a valid operation; it does not create duplicate tags.
  • 6c. Saving fails. The complete batch remains in memory, the saved file is unchanged, and TrackCall reports the storage error. The use case ends without confirmed persistence; recovery follows rule 10.

Removing a tag required by an active filter can hide the affected members after step 7. It does not delete them. Counts still refer to the target set fixed at step 6.

UC04: Remove one member

Related stories: US05, US06, US25, US34.

Goal: remove one unwanted record while retaining other members.

MSS

  1. The secretary lists, searches, or filters the roster.
  2. TrackCall displays the resulting records and their current indices.
  3. The secretary checks the intended member's details and requests deletion using its displayed index.
  4. TrackCall validates the request and asks for confirmation, naming the member, their displayed number, and their tags.
  5. The secretary confirms the deletion.
  6. TrackCall removes that record, saves the roster, and renumbers the remaining displayed records while retaining the active search and filters.
  7. TrackCall reports the deleted record. The use case ends.

Extensions

  • 1a. The listing, search, or filter command is invalid. TrackCall reports the error and preserves the current view. The secretary can retry step 1.
  • 2a. The result is empty. No member can be selected. The use case ends without changes.
  • 4a. The deletion command or index is invalid. TrackCall reports the error and removes nothing. The secretary checks the current list and retries step 3.
  • 5a. The secretary enters y or yes in another letter case. TrackCall reminds them to type yes exactly and keeps the confirmation pending. The use case resumes at step 5.
  • 5b. The secretary enters anything else. TrackCall cancels the deletion, removes nothing, does not run that input, and does not save. The use case ends.
  • 6a. Saving fails. The record remains deleted in memory but may return after restart. TrackCall reports the storage error and leaves the saved file unchanged. The use case ends without confirmed persistence; recovery follows rule 10.

Deletion has no undo after confirmation. It removes the underlying record, not just its visible card.

The command is delete INDEX, where INDEX is one positive ASCII-digit index from the current displayed list; leading zeroes are accepted. Signs, decimals, letters, whitespace inside the index, extra arguments, and out-of-range indices are rejected.

After the updated roster is saved, successful deletion reports Deleted member followed by the member's name and tags. A save failure reports Could not save data due to the following error: [DETAILS] with retry guidance; the deletion remains in memory, but the previous saved file is preserved.

UC05: Reset the whole roster

Related story: US07.

Goal: remove all member records, including records outside the current view.

MSS

  1. The secretary decides to remove all records and requests clearing the roster.
  2. TrackCall validates the request and shows the total stored-member count, including hidden members.
  3. The secretary confirms with yes. TrackCall removes every member.
  4. TrackCall saves the empty roster, clears the search, tag, and selection filters, and reports the number removed. The use case ends.

Extensions

  • 2a. The command contains extra arguments. TrackCall rejects it without changing anything. The secretary can retry step 1.
  • 2b. The roster is already empty. TrackCall still attempts to save it and reports that no changes were needed only if saving succeeds. No confirmation is needed. The use case ends. If saving fails, extension 4a applies.
  • 3a. A reply of y or yes in another letter case shows a reminder and keeps the confirmation pending. The use case resumes at step 3.
  • 3b. Any other reply cancels without running that input. Records, view, and saved data stay unchanged. The use case ends.
  • 4a. Saving fails. TrackCall restores the previous records, displayed list, and filters and leaves the saved file unchanged. It reports that no members were removed. The secretary can resolve the storage problem and retry step 1.

There is no undo after confirmation. Recovery after a successful clear requires a usable backup, such as the automatic previous-version backup.

  2. TrackCall displays a local summary of all commands available in the running version.
  3. The secretary requests one command's details, for example help tagall.
  4. TrackCall displays that command's purpose, syntax, examples with expected results, parameter rules, and errors. The use case ends.

  • 3a. The topic is unknown or uses the wrong case. TrackCall reports that there is no help entry for that topic and suggests help to list commands. The secretary can retry step 3.

UC07: Load a manually edited data file

Related stories: US11, US12, US14.

Goal: load valid corrections made outside the app.

Preconditions: TrackCall is closed and the secretary has backed up the data file.

MSS

  1. The secretary edits and saves the JSON data file while preserving its structure and valid member fields.
  2. The secretary starts TrackCall.
  3. TrackCall validates the complete file and loads its members in file order.
  4. TrackCall displays the loaded roster. The secretary checks the corrections. The use case ends.

Extensions

  • 1a. TrackCall is still running when the file is saved. The next save is refused with a warning and the change stays in memory. The secretary exits and restarts to keep the edit (resume at step 2), or runs a roster-changing command to replace it; the edited version is then kept in .bak.
  • 3a. The file is missing. TrackCall loads sample members and logs that the file was missing. It creates the file only after a valid data-changing command saves successfully. The use case ends.
  • 3b. The file is invalid or unreadable. TrackCall preserves its bytes in a uniquely named recovery copy and opens a dialog before the roster can be edited. The secretary can restore a valid backup, start with an empty roster, or close without replacing the file. No partial roster is loaded. The use case ends after the chosen recovery action.
  • 3c. TrackCall cannot preserve the damaged file. It reports the failure and closes without opening an editable roster. The secretary fixes access or restores a backup, then retries step 2.

The file uses UTF-8 JSON with a persons array. TrackCall writes name, phone, email, and address fields and a tags array of strings for each member. An empty address represents no provided address. Loading treats a missing or null tags field as an empty array. Member values follow rule 3 for tags. Missing or null required contact fields, invalid values, null entries, duplicates under the legacy exact-contact storage rule (rather than normalized-name input matching), comments, and trailing commas invalidate the file. Repeated identical tags collapse into one assignment. Unknown member fields are ignored, repeated fields keep their last value, and JSON numbers in text fields are accepted as text. {"persons": []} is a valid empty roster.

Do not edit the data file while TrackCall is running. Keep a backup before manual changes. If the file is changed while TrackCall is running, the next save is refused with a warning instead of silently replacing the outside changes.

Non-functional requirements

These are acceptance requirements for the intended product, not verified results for the current build. They include relevant course product constraints. The performance workload is a test target, not a restriction on accepted records or command length.

ID Quality or constraint Acceptance requirement
NFR01 Platform compatibility The released application runs on Windows, macOS, and Linux with Java 25, without needing a second Java version.
NFR02 Portable distribution The release is a single JAR no larger than 100 MB. Running it requires no installer or separately installed application dependencies beyond the compatible Java runtime.
NFR03 Offline availability Core roster management and in-app help remain usable with networking disabled. They do not depend on a team-operated server.
NFR04 Keyboard usability After launch, every in-app MVP operation can be completed using typed commands and keyboard navigation, without a required mouse action. Manual file editing uses an external text editor.
NFR05 Display usability At 1920 x 1080 or higher with 100% or 125% scaling, controls and text remain readable without layout overlap. At 1280 x 720 or higher with 150% scaling, every function remains usable. Long rosters and help text remain accessible by scrolling.
NFR06 Local data privacy Core operations do not transmit member records to external services. The MVP provides no login or encryption; protection of the local file relies on the user's operating-system access controls.
NFR07 Inspectable storage Member data is stored locally as human-editable UTF-8 JSON, with no DBMS required. The saved data can be read and corrected using an ordinary text editor while the app is closed.
NFR08 Response time Each valid in-app command completes within 2 seconds under this workload: 500 members, a writable data file up to 1 MB, and commands up to 256 characters. Test hardware: 2 GHz dual-core CPU, 4 GB RAM, and local SSD, with no competing heavy workload. Measure from submission to displayed result, including any save; exclude startup and shutdown. Record the OS, Java version, hardware, dataset, and timings when testing.
NFR09 Persistence reliability After a data-changing command reports success, a normal restart retains the saved roster. A simulated write failure leaves the previous saved file intact and is never reported as success. In-memory recovery follows rule 10, including the rollback required for clear. The exit command closes normally without performing an extra save or corrupting the last successfully saved roster.

Input validation, duplicate rejection, filtering, and no-op behaviour are functional requirements and are recorded in the shared rules instead of being counted as NFRs. Development-process rules, such as incremental delivery, are also not product NFRs.

Term Meaning
Membership secretary The single operator responsible for keeping a club or organisation's member roster up to date.
Roster / address book The complete collection of member records, including records hidden from the displayed list. The file and starter code use the term address book.

Group A set of members sharing a tag, such as a committee or cohort. Groups are not separate stored objects in the MVP.
Tag A label containing 1 to 30 ASCII letters or digits with optional internal hyphens, matched without regard to case and assigned at most once to each member.

Tag rename Replacing one tag with another for every displayed member who has it (renametag).
Confirmation prompt The pending question shown after delete INDEX or a non-empty clear. Only yes confirms; y or yes in another letter case keeps it pending; other input cancels.
Outside edit A valid change made to the data file while TrackCall is running; the next save is refused once.
Duplicate record New input whose normalized name and trimmed phone, email and address match another record. Name capitalization and repeated whitespace are ignored; tags are ignored. Legacy JSON loading retains its original exact identity rule.
No-op A valid operation that leaves record values unchanged. A valid data-changing no-op can still retry saving; a bulk command with no targets is an error.
In-memory data The working roster held by the running app. After a save failure it can differ from the file and may be lost on exit.
Persisted data The roster successfully written to the local data file and available for a later session.

Exit command The parameterless exit command that closes TrackCall without changing records or performing a final save.

vCard A contact-card file format considered for exporting member contact details to phone or contact applications. It is outside the selected MVP.

v1.5 release candidate changes

  • AppInstanceLock obtains a nonblocking OS file lock before production startup reads preferences or the roster. A second launch from the same JAR folder fails with an already-running explanation. MainApp retains the lock through preference saving and releases it on exit or failed initialization. The persistent lock file is never deleted; the OS releases its lock if the process terminates.
  • JsonAddressBookStorage rotates the backup only when the existing valid roster differs from the requested member list. It still attempts the actual save for unchanged commands, preserving retry behavior while keeping the previous distinct version recoverable.
  • edit INDEX a/ clears the optional address. Add still rejects a supplied blank address.
  • Import save errors retain the existing batch and now include the same unsaved-change warning and recovery instructions as other data-changing commands.
  • The active-filter area has a bounded, vertically scrollable viewport. Long labels use ellipsis and full-text tooltips, while removal buttons keep their width. Keyboard focus scrolls the corresponding box into view and moves to another box after removal, or to the command field when no boxes remain.
  • Details-panel tags wrap within the available width so every valid 30-character tag remains readable.
  • Export reserves application and recovery paths without regard to case, including absent files and parent-directory spelling. Directory destinations produce a handled error.
  • Email validation messages and offline add/edit help explain the existing ASCII and single-separator rules. Tag validation and tag feedback share the model constraint and formatter. Search commands use the same whitespace splitting, and duplicate-prefix errors have a stable field order.
  • Routine command/result/model logs omit member contact values. Save-failure diagnostics record the command and error type without raw exception messages or cause chains, which can contain stored JSON. Existing logs are not rewritten.

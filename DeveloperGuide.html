Developer Guide

TrackCall helps club secretaries maintain member contact details and organise overlapping groups. Users can search by name or email, filter members by tags, update group tags in bulk, and import or export rosters as CSV files.

This guide describes the v1.5 release candidate. Use the User Guide for command syntax and the sections below for implementation decisions and failure handling.

Architecture

The architecture diagram shows the main components and their dependencies.

Main components

Main manages startup and shutdown through two classes: Main and MainApp.

  • At startup, it acquires the application-instance lock, initialises preferences and components, then loads or recovers the roster before opening the main window.
  • At shutdown, it stops the components and runs their cleanup methods.
Component Responsibility
UI Display the interface and receive user input.
Logic Parse and execute commands.
Model Hold the app's data in memory.
Storage Read and write data on disk.
Commons Provide classes shared by multiple components.

Component interactions

The sequence diagram shows how the components handle delete 1 and the yes that confirms it.

Each of the four main components defines an API through an interface with the component's name. A corresponding manager class implements that interface. For example, Logic.java defines the API and LogicManager.java implements it.

Components communicate through these interfaces. This reduces their dependence on each other's implementation details, as shown below.

UI component

API: Ui.java

Structure

  • MainWindow contains the command box, result display, member list, details panel and status bar.
  • These visible parts extend UiPart. JavaFX layouts are defined in src/main/resources/view.
  • HelpWindow builds command cards from CommandHelp in Logic.
  • WindowPlacement restores a usable window position and size.
  • MainApp opens RosterRecoveryDialog before exposing an invalid roster for editing. The dialog shows the loading failure cause so the user knows what to correct.

Interactions

  • Call the Logic interface to execute commands.
  • Observe model data so displayed records update when data changes.
  • Use Person and other model values to render the selected member's details.

Logic component

API: Logic.java

The following sequence diagram illustrates parsing and executing delete 1 to request confirmation.

The sequence shows a valid displayed index. The parser creates a deletion request, while the command resolves the member through Model. It returns a confirmation command without deleting or saving anything. The separate confirmation sequence below shows the later mutation. Temporary parsers are left to Java garbage collection, so their lifelines have no destruction marker.

Command execution

  1. AddressBookParser selects the matching parser, such as DeleteCommandParser.
  2. That parser produces a Command subclass, such as DeleteCommand.
  3. LogicManager executes the command. The command interacts with Model as needed.
  4. Logic returns a CommandResult containing the result.

XYZCommand represents concrete commands with the same execution contract. isReadOnly() tells LogicManager whether to save the roster after execution. Export is read-only with respect to the roster even though it writes a separate CSV file.

Deletion confirmation

Flow

  1. Request: DeleteCommand validates the displayed index. It returns a prompt and a ConfirmDeleteCommand holding the selected Person. No record changes or save occur yet.
  2. Wait: LogicManager retains the pending command. MainWindow highlights the command box and displays the confirmation hint.
  3. Answer: the next input bypasses AddressBookParser.
    • Exactly yes in lowercase, after trimming surrounding whitespace, executes the pending deletion and saves.
    • A near miss (y, Y, YES, Yes) never confirms. Confirmation#isNearMiss detects it, and LogicManager keeps the deletion pending and repeats the prompt with a reminder to type yes exactly.
    • Any other input cancels. That input is consumed, not executed as another command. If it starts with a command word, the cancellation message says that the command was not run.
  4. Finish: clear the pending command once the deletion runs or is cancelled. A later yes cannot repeat the deletion.

Safety and failure handling

  • Store the Person, not its index. Removing a filter while waiting cannot redirect the deletion.
  • If a filter is removed, show the confirmation prompt again beneath the filter feedback.
  • If saving fails, keep the deletion in memory and show retry guidance. See save failures.
  • Without a pending confirmation, yes is an unknown command.

Design decisions

  • A typed confirmation preserves the keyboard workflow; a modal pop-up would interrupt it.
  • The confirmation word is the full word yes, with no shortcut, to prevent accidental deletion or clearing. A single y is easy to send by a stray keystroke, by habit from earlier prompts or by auto-repeat. Requiring the whole word, in lowercase, makes confirmation a deliberate act for an action with no undo.
  • A near miss keeps the prompt pending instead of cancelling or confirming. The user is not forced to repeat delete or clear after a typing slip, and the slip is never treated as consent.
  • Consuming cancellation avoids treating replies such as no as new commands.

Parsing classes

  • Dispatch: AddressBookParser selects a command-specific parser and returns its Command.
  • Parser contract: command-specific parsers implement Parser. XYZCommandParser represents concrete classes such as AddCommandParser.
  • Tokenization: ArgumentTokenizer splits prefixed fields into an ArgumentMultimap. CliSyntax defines the known Prefix values.
  • Value conversion: ParserUtil validates and converts indexes and member fields.
  • Prefix checks: add/edit parsers use PrefixValidator to reject unsupported field prefixes.
  • Tag checks: tag, untag, bulk-tag and rename parsers share BulkTagArgumentParser. It recognises n/, p/, e/ and a/ only to reject them with command-usage guidance.

Model component

API: Model.java

The model separates stored records from display state. The diagrams show one responsibility at a time.

1. Stored records and preferences

  • ModelManager holds an AddressBook and UserPrefs.
  • AddressBook owns a UniquePersonList. It exposes a live, unmodifiable list of members.
  • UserPrefs holds window settings. Other components read it through ReadOnlyUserPrefs.
  • Model has no dependency on UI, Logic or Storage.

2. Member values

  • A Person references a name, phone, email, address and a set of tags.
  • An absent address is an empty Address value, not a missing object.
  • Contact values and tags are immutable and can be reused when replacing a record. Associations therefore fit these references better than exclusive composition.
  • There is no separate shared tag registry.

Contact identity: Person#isDuplicateContactOf checks new add/edit/import input against the whole roster, including hidden members. It ignores name case and repeated whitespace, compares the phone after removing ASCII spaces, compares email local parts exactly and domains without regard to ASCII case, and compares trimmed addresses exactly; tags are ignored. A phone's leading + remains significant. Name case is compared with equalsIgnoreCase after whitespace is collapsed, not by lowercasing, because lowercasing changes Greek sigma by its position in the word. Person#isSamePerson retains exact name matching for JSON loading, so older name variants remain loadable. EditCommand checks for duplicates only when contact details change; tag-only and unchanged-contact edits remain possible on those records.

3. Display pipeline

  • FilteredList applies the current conditions to stored records.
  • getFilteredPersonList() returns this filtered view in stored roster order; indexed commands use it.
  • sort reorders the complete stored roster, including hidden members. There is no separate display-sort mode.
  • Changing conditions does not reorder records.

4. Filter state

The view is either showing all members or narrowed by one or more conditions. This state diagram shows which commands move it between the two.

The class diagram below shows how ModelManager stores those conditions.

  • activeFilters contains removable name, email, tag and show conditions in application order.
  • Each show condition wraps a PersonSelectionPredicate; additionalFilters holds other internal predicates.
  • refreshFilteredPersons() combines all conditions with AND.
  • Record replacement updates selected references; deletion removes the member from each selection.
  • Each distinct selection has a Show: N selected chip. Removing it clears only that condition. list clears all conditions while preserving stored order.

Design rationale: changing conditions does not rewrite the JSON roster. Export follows the displayed members in their stored order. JavaFX transformation lists let the UI observe updated results while commands continue to resolve indexes against exactly what the user sees. Selection predicates need special handling because edits replace Person objects: setPerson(...) updates their selected references before refreshing the view.

Storage component

API: Storage.java

Responsibilities

  • StorageManager delegates roster JSON to JsonAddressBookStorage and preferences to JsonUserPrefsStorage.
  • ImportCommand and ExportCommand call the CSV helpers directly.
  • CsvAddressBookCsv provides their shared header and format. Commons CSV handles quoting and escaping.
  • Export snapshots Model#getFilteredPersonList() and reports hidden-member counts when applicable.
  • CSV export is a user-requested copy. It does not replace automatic JSON persistence.

Write safeguards

  • LogicManager gives export the active roster and preferences paths for destination checks.
  • Protected destinations include those files, backups, recovery copies, the running JAR and session lock.
  • FileUtil#writeAtomically is the core helper. It lets the caller write a complete replacement to a sibling temporary file, then atomically replaces the target. The destination's parent directory must already exist. CSV export and backup copies call it directly.
  • FileUtil#writeToFile wraps it for text content: it creates missing parent directories first. JSON roster saving reaches it through JsonUtil.
  • On failure, preserve the previous destination and attempt temporary-file cleanup.
  • An export's parent directory must already exist.

See saving and recovery for JSON failures and CSV export for its separate write workflow.

Common classes

Classes used by multiple components are in the seedu.address.commons package.

  • core: GuiSettings holds the window size and position saved in preferences, LogsCenter configures the shared loggers, and Index represents a one-based displayed index.
  • exceptions: IllegalValueException and DataLoadingException signal invalid values and unreadable stored data.
  • util: helpers for files (FileUtil, including atomic writes), JSON (JsonUtil), strings (StringUtil), collections (CollectionUtil), argument checks (AppUtil) and toString output (ToStringBuilder).

1. Offline command help

Purpose: show command instructions without a browser or network connection.

Flow

  1. HelpCommandParser accepts no topic or one known lowercase topic.
  2. HelpCommand returns the topic in a CommandResult.
  3. MainWindow calls HelpWindow#show(topic).
  4. HelpWindow reads the local CommandHelp entry and displays the card.

Rules and design

  • Keep the catalogue in Logic and window handling in UI. Commands do not construct windows.
  • Include all nineteen commands, each with syntax, examples, expected results and common errors.
  • help COMMAND and overview buttons open the same topic. F1 and the Help menu open the overview.
  • Use two card columns in wide windows and one in narrow windows.
  • Arrow/Page keys scroll; Home/End move to the ends; Escape closes help.
  • Help is read-only. Invalid or multiple topics do not open a new topic.
  • Design note: the catalogue is bundled in CommandHelp instead of linking to the hosted User Guide, so help works without a browser or network connection. CommandHelpTest checks that it covers every command.

2. List and clear commands

Purpose: restore the complete view with list, remove displayed members with clear, or remove everyone with clear /all.

List flow

  1. Clear predicates with updateFilteredPersonList(PREDICATE_SHOW_ALL_PERSONS).
  2. Preserve the current stored order, including an order saved by sort.
  3. Report the full count. Do not change records or save the JSON file.

Clear flow

  1. ClearCommandParser accepts clear or exactly clear /all; other arguments are rejected.
  2. prepareTargets(model) snapshots displayed members for clear, or the full roster for /all. A nonempty target set prompts with its scope and count. clear /all, and clear when every member is displayed, use Clear the entire roster? Total members: N. When members are hidden, clear uses Clear the N displayed member(s)? Hidden members will be kept. Use clear /all to remove everyone.
  3. Only lowercase yes, ignoring surrounding spaces, confirms. Near misses retain the original prompt; other input cancels without executing it. Removing a filter while waiting cannot expand the captured target set.
  4. Snapshot the complete roster, then remove only captured targets without changing selection metadata yet.
  5. Save the remaining roster. After a successful displayed clear, retain conditions and remove deleted members from Show selections; an emptied selection remains removable as Show: 0 selected. Whole-roster clearing resets conditions. list reveals any hidden survivors.
  6. On failure, restore the original records under the original conditions, preserving Show selections. Include the storage failure reason. A fresh clear or clear /all confirmation is needed to retry.

An empty displayed list with hidden records reports nothing to clear and suggests list or clear /all, without prompting or saving. An already-empty roster keeps the existing immediate-save retry behaviour.

SHOW_ALL in the diagram abbreviates PREDICATE_SHOW_ALL_PERSONS.

Outcome Records and view Command input
Save succeeds Remove only targets; displayed clear retains conditions, /all resets them. Clear the input.
Save fails Restore the snapshot under the original conditions and stored order. Retain the submitted input; run clear or clear /all again for the intended scope.

Rules and design

  • Clearing a non-empty roster requires confirmation and has no undo. It does not change preferences.
  • Clearing an already-empty roster attempts to save, allowing a retry after an unsaved deletion. An empty displayed list with hidden members never saves or removes those members.
  • Keep rollback in Logic because that layer knows the persistence outcome.
  • Atomic roster replacement is separate from backup rotation; see startup and validation.

SaveFailureException#isChangeApplied() lets the command box retain the last submitted input on clear rollback while clearing input for changes that remain applied. After a confirmed clear fails, the retained input is the answer yes; choose clear or clear /all again to start a fresh confirmation.

3. Name sorting

Purpose: save the complete roster in A–Z name order while retaining active conditions.

Flow

  1. SortCommand calls Model#sortPersonsByName() to reorder the complete stored roster, including hidden members.
  2. Name#getComparisonKey() strips surrounding Unicode whitespace and collapses repeated whitespace for comparison.
  3. Compare keys without regard to case; preserve stored spellings and the relative order of ties.
  4. LogicManager saves the reordered roster through the normal data-changing command path, even if empty or unchanged.
Operation Stored order Conditions
sort Stably reorder everyone A–Z. Retain.
list Retain, including a saved sort. Clear.
Valid import, applied add Append new members until the next sort. Clear.
find, findemail, filter, show Retain. Narrow the view.
Displayed clear Remove captured targets; retain survivor order. Retain after saving.
clear /all Empty the roster. Clear after saving.
Record or tag edit Retain each member's position until the next sort. Re-evaluate.

Rules and design

  • Indexed commands and export use the displayed subset of stored order. list and restart retain a saved sort.
  • Sorting has no confirmation because it removes no records. The original insertion order cannot be restored by a command.
  • Stable ties use the current stored order, including after edits and tag changes.
  • A failed save retains the reordered in-memory roster and reports the shared unsaved-change guidance.
  • Design note: sort reorders the stored roster instead of adding a display-only sort mode. This keeps one order for the view, indexes, export and persistence; a second ordering would force indexed commands and export to say which order they use, and would not survive a restart.
  • No descending or multi-field sorting is provided. PersistentSortTest and SortOrderIntegrationTest cover persistence, hidden members, stable ties, active conditions, later edits/appends and save failures.

4. Email search

Purpose: narrow the displayed members by an address or email fragments. find follows the same cumulative and repeat-detection rules for names.

Flow

  1. Parse a nonblank query into EmailContainsKeywordsPredicate.
  2. FindEmailCommand calls ModelManager#filterFilteredPersonListByEmail. If an equivalent email search is not already active, append one email ActiveFilter and reapply all active conditions with AND.
  3. Re-evaluate the live view and return its count with the feedback below. Retain stored roster order.

Rules and design

  • Split keywords on Java whitespace and Unicode space separators, including nonbreaking spaces. Lowercase keywords and email with Locale.ROOT; match literal substrings with OR within one command.
  • Do not search names or phone numbers. Regex syntax has no special meaning.
  • Keep earlier name searches, email searches, tag filters, show selections and stored order. Each distinct search adds its own box in application order; removing a box retains the other conditions, and list clears all.
  • Repeats: ActiveFilter#hasSameSearch compares keyword sets of the same kind, ignoring keyword case, order and repetition. Names use String.CASE_INSENSITIVE_ORDER and emails use Locale.ROOT lowercase, matching their predicates. A repeat keeps the original box and label. Both model search methods return whether a condition was added.
  • Feedback: a repeat reports that the search is already active. A different query that leaves the displayed count unchanged reports Results unchanged. and keeps its condition. Searches only narrow the list, so equal counts mean the same members remain visible.
  • An email edit can remove a record from the view without deleting it.
  • Blank input preserves the view. Searching never saves data.
  • Design note: email matching is a separate command so that find stays name-only and every condition box describes exactly one kind of search.

5. Member details and command messages

Purpose: keep the roster scannable, reveal selected members' contact details and explain command outcomes.

Display responsibilities

  • PersonCard: show index, name and sorted tags.
  • MemberDetailsPanel: show and copy the selected member's phone, email and address. Disable address copying when the selected member has no address.
  • Messages#format(Person): produce labelled contact lines and sorted tags for command results.
  • MainWindow: hide contact lines from successful add/edit/delete command messages.
  • UntagCommand: return name and remaining tags directly, without contact fields.
  • ResultDisplay: display, wrap and scroll command results and errors. Split panes let users resize the working areas.

Interaction rules

  • Clear selection before executing any command, including commands that fail.
  • This clears the highlighted row and its details only. A show selection is a model predicate and remains active unless the command explicitly clears it.
  • F2 focuses the roster. Escape clears selection and hides details.
  • Report data-changing success only after saving. Explain unsaved changes separately.
  • Use LightTheme.css for shared colours and HelpWindow.css for help cards.

Window placement

  1. WindowPlacement checks saved bounds against available screens.
  2. Keep a usable position; otherwise choose the screen with greatest overlap, or the primary screen.
  3. Clamp off-screen or oversized bounds to the chosen screen. Replace invalid dimensions.

6. Saving and recovery

Purpose: persist valid record changes and recover safely when storage is unavailable or invalid.

Save flow

  1. Parse and execute the command.
  2. Return immediately for read-only commands, deletion/clear prompts or cancellations.
  3. Save the complete roster for valid data-changing commands, including no-ops.
  4. Return success only after saving. Parsing or execution errors do not save.

Atomic writes

  • StorageManager delegates roster writes to JsonAddressBookStorage.
  • The default path is data/addressbook.json, relative to the JAR folder in packaged builds.
  • JsonUtil calls FileUtil#writeToFile, which creates missing parents and delegates to FileUtil#writeAtomically to write UTF-8 to a sibling temporary file. Backup copies call writeAtomically directly.
  • Close the writer, then replace atomically. If atomic replacement is unavailable, report failure.
  • Preserve the previous target on failure and attempt temporary-file cleanup.

Save failures

Command In-memory state Retry behaviour
clear, clear /all Restore prior records and view. Resolve the cause before repeating the intended scope; confirm if prompted. A lone yes cannot retry.
Other data-changing commands Keep the applied change. Clear the input to prevent accidental repetition.
  • SaveFailureException records whether the change remains applied.
  • clear reports its failure message followed by the underlying storage error, including outside-change warnings. If external edits may exist, restart to load them; retry clearing only when intentionally replacing the outside version with the remaining in-memory roster. clear /all replaces it with an empty roster.
  • The previous roster file is unchanged. Exiting can lose unsaved in-memory changes.
  • After restoring access, inspect the list and use edit with an existing value to retry saving.
  • If no records remain, use clear. Exit never retries a roster save.
  • Preferences are saved separately during startup and shutdown.

Startup and recovery

  1. Acquire AppInstanceLock before reading preferences or the roster.
  2. Load valid records in stored order. A missing file loads sample members.
  3. For invalid data, preserve the exact bytes in a unique .corrupt-....json copy.
  4. Show the loading failure reason after Reason:: UTF-8 errors, JSON line/column syntax errors, a missing persons list, or an invalid member field. Offer a validated backup, an empty roster, or closing without replacement.
  5. Verify the original still matches its preserved copy before recovery replacement.
  6. Reload the recovered roster through the same storage instance to refresh its saved-data baseline.

Malformed JSON diagnostics include a syntax hint to check nearby commas, quotes and brackets, without showing file contents. A missing or null persons list also explains the required JSON object/list shape.

Safeguards and limits

  • Hold the instance lock through shutdown. A second instance is rejected; do not delete the lock file.
  • Accept one optional leading UTF-8 byte-order mark in JSON. Trim surrounding member-field and tag whitespace; name case and internal spacing are preserved.
  • Reject null roots, null members, null tags and invalid or duplicate member values.
  • Preserve an empty address, but reject a non-empty address that is blank after trimming or contains only Unicode spaces.
  • JSON loading retains Person#isSamePerson: compare all four trimmed contact fields exactly and ignore tags, so older name variants remain loadable.
  • Preservation failure prevents an editable roster from opening.
  • Normal saves validate the existing roster and rotate .bak only when stored member values differ, including tag spelling. A capitalization-only tag change therefore creates a backup.
  • An unchanged save still retries the write but retains the previous distinct backup.
  • saveWithBackup preserves the old backup while replacing the active roster. A failed roster write attempts to restore that backup; if rollback also fails, the temporary backup copy is retained.
  • Before saving, compare the valid file with the last loaded or saved roster. The first save after detecting an outside edit is refused and records the outside version as the new baseline. Restart to load that version, or retry saving to replace it while keeping its exact bytes in .bak, even if its member values match the requested save. This backup requirement stays pending after a failed write and clears after a successful save or an explicit reload.
  • A roster file created externally after a missing-file start is also detected, because storage records that it observed the file as missing.
  • Invalid preferences fall back to defaults. Logger initialisation failure falls back to the console.

7. Command parsing

Purpose: reject malformed input before changing data or view state.

  1. AddressBookParser reads a case-sensitive keyword and selects its parser.
  2. Command-specific parsers check argument structure, indexes and field values.
  3. Add/edit use tokenized prefixes and PrefixValidator. Tag commands use BulkTagArgumentParser to validate tag values and reject other member-field prefixes.
  4. A successful parse returns a Command; failures return usage or field guidance.

Rules

  • Add/edit accept fields in any order and reject repeated non-tag prefixes.
  • Reject unsupported whitespace-delimited ASCII single-letter prefixes in add/edit, including wrong-case prefixes.
  • Preserve standalone c/o, s/o, and d/o abbreviations in any letter case, URLs, numeric slashes and slashes embedded within words in add/edit. A/ followed by a digit is also literal within an address, as in Block A/12. A supported lowercase prefix still ends the address.
  • Field validation lives in the model value classes (Name, Phone, Email, Address, Tag) through isValidXyz methods, not in the parsers. The command parsers, the JSON loader and the CSV importer therefore apply one definition per field. The User Guide lists the accepted formats. Address is the only optional field: an empty value is valid, but a non-empty value must contain a character other than whitespace or Unicode spaces, so edit can tell "clear the address" from "blank address".
  • Tag parsers name unsupported member fields, preambles and missing t/ prefixes in their diagnostics. Invalid tag values receive the specific reason followed by the command usage.
  • clear accepts only an optional /all; list, sort and exit take no arguments. Each other command enforces its own grammar.

8. CSV import

Purpose: validate an entire file before appending unique members.

Flow

  1. ImportCommandParser accepts one p/FILE_PATH; quote paths containing whitespace. It rejects an empty path, unmatched quotes, unquoted whitespace and trailing arguments. For trailing arguments, it reports a repeated p/ or an unknown single-letter prefix such as x/.
  2. Resolve the path and validate the complete CSV before changing the model.
  3. Skip duplicates against the stored roster and earlier accepted rows.
  4. Append unique records in source order; clear conditions while preserving existing stored order.
  5. Save through LogicManager, even if the file is header-only or all rows are duplicates.

Validation and failure rules

  • Require a case-insensitive .csv extension. Preserve path case.
  • Folder restriction: the app never reads or writes files outside the folder that holds the JAR. In a packaged build, FileUtil#resolvePath resolves a relative path from that folder and rejects a path that leaves it, such as one using .. or an absolute path elsewhere (Files must stay inside the JAR folder: ...). It also rejects any path component that is a symbolic link, or whose real location is outside the folder, even when a link's target is inside it (Symbolic links are not allowed in application file paths.). An absolute path inside the folder is accepted. Each rejection is reported as Could not import CSV: followed by the reason, and changes nothing. Development runs are unrestricted so that test fixtures can use temporary folders. Export applies the same check.
  • Treat only a single letter followed by / as a parameter prefix, so a folder name such as backup-2026/ is not reported as an unknown prefix. Uppercase P/ is an unknown prefix, not a repeated p/.
  • Reject files over 10 MiB and more than 10,000 nonblank member rows before duplicate removal. Bound the byte read as well as checking file size, so a growing source cannot bypass the limit.
  • Read strict UTF-8, allowing an optional byte-order mark.
  • Require the five headers in any order; validate CSV quoting and every member field.
  • Trim surrounding field/tag whitespace. Reject embedded line breaks.
  • Skip blank records but include them when reporting physical row numbers.
  • Report a missing source with its resolved path and ask the user to check its name and location. Other read failures, including directories, use the platform's I/O error text and do not always include the path. Reject repeated or unknown prefixes.
  • Read or validation errors leave records, the view and saved data unchanged. Never modify the source CSV.
  • Save failures keep the imported batch in memory and report retry guidance.

Design: whole-file validation prevents partial imports. Person#isDuplicateContactOf provides the same duplicate check as new add/edit input, including normalized names, phone spacing and email-domain case. The email local part remains case-sensitive; trimmed addresses compare exactly. Commons CSV handles quoting instead of manual string splitting.

9. CSV export

Purpose: export displayed members, in displayed order, without changing the view or automatic JSON file.

Flow

  1. LogicManager supplies protected roster and preferences paths to ExportCommand.
  2. Parse the path, rejecting any double quote before checking the extension, then resolve and validate the destination before writing.
  3. Snapshot and export the displayed members in their current order. Report how many stored members were excluded.
  4. Return the exported count and path; include the hidden-member count when any were excluded. Do not save the automatic JSON roster.

Overview: sd ExportRoster

Detail: sd CheckExportDestination

Detail: sd WriteCsvAtomically

Rules and design

  • Write UTF-8 with a header row. Sort each member's tags and join them with semicolons.
  • Use Commons CSV for quoting and escaping. An empty displayed list produces a header-only file. Run list before exporting to include everyone.
  • ExportCommandParser requires a .csv extension, ignoring letter case.
  • Reject a double quote anywhere in the path, including directory names, because import cannot read such filenames. Spaces need no surrounding quotes, unlike import.
  • Require an existing parent directory and reject a directory as the destination; apply packaged file-location restrictions.
  • Report missing/non-directory parents and write failures with actionable messages instead of temporary-file paths.
  • Close the CSV writer before atomic replacement. Attempt temporary-file cleanup on failure.
  • Preserve an existing export if writing fails. Keep roster data, filters and stored order unchanged.
  • Reject aliases of protected files by checking existing file identity as well as normalised paths.

10. Selecting displayed members

Purpose: narrow the current view using displayed indexes.

  1. Validate every requested index before changing the view.
  2. Resolve indexes against the displayed view and create a PersonSelectionPredicate.
  3. Unless the same member set is already selected by an active show condition, append a SHOW-kind ActiveFilter containing the selection predicate.

Rules

  • Repeated indexes collapse to one member. Argument order does not reorder the display.
  • Each show can only narrow the view. Record replacement updates selected references.
  • Each distinct selection has a Show: N selected chip in command order alongside other filters. Its tooltip lists selected names alphabetically, ignoring case. Repeating the same member set creates no extra chip.
  • Removing a chip removes only that selection. Its count reflects the remaining selected records, including those hidden by other conditions. Deleting every selected record leaves a removable Show: 0 selected chip.
  • list, applied add, successful clear /all and valid import clear selections; displayed clear retains conditions and updates Show counts.
  • Show is read-only and does not save.
  • Design note: a selection is a predicate over Person references, not remembered indexes, so it stays correct when other conditions renumber the view. The cost is updating those references when setPerson replaces a record (see Model component).

11. Tag filtering

Purpose: narrow the view to members matching at least one tag in a command, ignoring case.

Flow and rules

  1. FilterCommandParser accepts filter t/TAG [t/MORE_TAGS]... and validates every value with BulkTagArgumentParser#parseTagName. An invalid value rejects the whole command before changing the view.
  2. FilterCommand deduplicates tags, retaining their first spelling and argument order.
  3. ModelManager#filterFilteredPersonListByTags adds one ActiveFilter for that alternative group. Its predicate uses OR within the group. The model combines all active conditions using AND. Thus filter t/a t/b, then filter t/c, means (a OR b) AND c.
  4. A repeated group, ignoring case and order, retains its original condition and reports that it is active. Other name/email searches, Show selections and stored order remain. Zero matches are successful.
  5. The condition's X removes that entire group. Keep predicates active so later record edits re-evaluate matches.

Labels and results

  • ActiveFilter#ALTERNATIVES_SEPARATOR joins alternatives with /, avoiding ambiguity with a tag named or. This also applies to name and email keyword labels: Name: Alice / Tan.
  • Tag labels show at most ActiveFilter.MAX_SHOWN_TAGS (4) values, then +N more. getFullLabel() supplies every alternative to the tooltip and remove button's accessible text.
  • A comma between tag conditions means AND; / inside a condition means OR. When several conditions appear, FilterCommand#formatCondition parenthesizes groups: ("a" / "b"), "c".
  • A member updated by a tag command remains visible if another alternative still matches.

Tests: FilterCommandParserTest, FilterCommandTest, ModelManagerTest and MainWindowTest cover OR/AND combinations, repeated groups, invalid values, counts, truncated labels, tooltips and accessibility.

12. Individual tag editing

Purpose: add or remove one tag without replacing the member's other tags.

  1. Resolve the member from the displayed index.
  2. Copy the tag set and add or remove the requested tag.
  3. Construct a new Person with unchanged contact fields and call Model#setPerson.
  4. Save the complete roster and report the result.

Rules

  • Retain searches, filters, stored order and show selections. Removing a required tag can hide the record.
  • Match tags ignoring case. An existing addition or absent removal is a valid no-op and still saves. Keep the stored spelling when skipping an already-present tag.
  • Invalid indexes or arguments fail before saving. Applied-but-unsaved changes remain in memory.
  • The shared tag parser rejects member-field prefixes (n/, p/, e/, a/) with command usage.
  • Design note: tag and untag copy the tag set and change one entry, whereas edit INDEX t/... replaces the whole set, so adding one tag with edit means retyping the rest.

13. Bulk tag editing

Purpose: update one tag for every displayed member.

Input: TagAllCommandParser and UntagAllCommandParser share BulkTagArgumentParser. Require exactly one valid t/TAG.

  • BulkTagArgumentParser reports each failure with its own diagnostic: a missing t/, text before t/, a member-field prefix (n/, p/, e/, a/), an empty tag, more than one t/, an unsupported character, whitespace inside a tag, misplaced hyphens, or excess length. Every diagnostic is followed by the calling command's usage. The User Guide gives the wording.
  • Unsupported characters are checked before length, so non-ASCII code points are not misreported as overlong ASCII tags. Invisible control characters are shown as code points, for example U+0000.
  • These argument errors give the reason followed by usage without a generic format-error header. Existing index parsing in tag and untag retains its format-error header.

Flow

TagAllCommand and UntagAllCommand inherit this flow from BulkTagCommand#execute.

  1. Snapshot the displayed list. This prevents updates from changing the targets mid-loop.
  2. Reject an empty target set before saving, with guidance to run list or choose a group using find or filter.
  3. Replace each target that needs a change, preserving contact fields and unrelated tags.
  4. Count changed and skipped members against the original snapshot, then save the full roster. Feedback explains case-insensitive matching and adds No changes were made. when all targets were skipped. If untagall hides updated members through an active filter, TagUpdateUtil#describeHiddenUpdates also reports the current list and suggests list.

untagall changes only the subclass update rules; renametag follows the same displayed-target/save pattern through its own parser.

Design tradeoff: iterating the live filtered list would let an update hide a member and shift the remaining indexes. A snapshot fixes membership for the whole operation. Replacement Person objects preserve unrelated values and trigger the observable view to re-evaluate.

Shared implementation: TagAllCommand and UntagAllCommand extend the abstract BulkTagCommand. It owns the snapshot, the empty-list rejection, the skip-and-count loop and the feedback. A subclass supplies only needsUpdate(Person), the membership check, and updateTags(Set<Tag>), which adds or removes the tag. tagall updates members who lack the tag; untagall updates members who have it. LogicManager saves the roster afterwards, as for any data-changing command.

Rules and design

  • Never visit hidden members. Removing an active filter tag can hide targets after their update.
  • Retain conditions and stored order. Skip redundant assignments rather than rejecting the batch.
  • A valid all-skipped batch still saves. A save failure leaves the complete batch in memory.
  • The shared base class keeps targeting, logging and feedback consistent between add/remove operations.
  • Acting on the whole roster would prevent group targeting; list supplies that behaviour when wanted. Explicit index lists would be error-prone for large groups; show can choose a precise target set first.

Renaming within the displayed group

RenameTagCommand extends Command directly instead of BulkTagCommand. It handles two tags, rejects an old tag that no displayed member has, and counts merges as well as changes, which the shared loop does not. Like BulkTagCommand, it snapshots the displayed members before updating them.

  1. RenameTagCommandParser uses BulkTagArgumentParser#parseTagValues to require exactly two tags; a different count is reported with the number received and a reminder that the current tag comes first. It rejects preambles, other member-field prefixes and identical spellings, and allows case-only renames so a group can use one capitalization. BulkTagArgumentParser#parseTagName validates each value, so invalid tags give the same diagnostics as tagall and untagall.
  2. Snapshot displayed members with the old tag, matching without regard to case. Leave hidden members unchanged.
  3. Reject an old tag that no displayed member has. If hidden members have it, report their count and suggest list. Otherwise replace it on targets requiring a change.
  4. Merge a distinct already-present new tag into one assignment; report changed and merged counts. A case-only rename skips members already using the requested spelling and does not count them as merges.
  5. Retain conditions and stored order and save the complete roster. Report members hidden by an active filter after renaming, and the count of hidden members that still retain the old tag. A case-only rename that changes nobody reports that every displayed member already uses the requested spelling.

All three bulk tag commands, although they do not share one base class, use the displayed list so the secretary can limit a change to a reviewed group. Run list first to rename across the whole roster. When merging into an existing tag, retain the spelling typed in the command. Tag#equals ignores case while tagName preserves spelling, so after filter t/committee, renametag t/committee t/Committee keeps matching members visible. Renaming to a different tag name leaves the old filter active and hides the renamed members without deleting them. Rejecting an unused current tag catches likely typos; allowing case-only renames supports consistent spelling.

Known limitations

  • JSON uses a persons array and member tags arrays. Unknown fields are ignored and repeated fields retain the last value. Numeric JSON values in text fields become text. Comments and trailing commas fail.
  • Deletion and clearing a non-empty roster require confirmation. Neither has undo after confirmation.
  • The backup retains the previous distinct saved roster, not a full history. Later changed saves replace it.
  • Names are compared and searched as entered, without Unicode normalisation. Sorting uses Java's case-insensitive order, so accented names can sort after Z.
  • After an accidental clear, stop changing data and follow the manual recovery steps.

Shared behaviour rules

These contracts apply across commands. Feature sections explain their implementation and exceptions.

  1. Input validation: use lowercase keywords and prefixes; trim surrounding field whitespace. Reject invalid input before changing records, filters, stored order or files. Submitting any command still clears the highlighted row and its details. See command parsing for field rules.
  2. Duplicate identity: add/edit/import compare normalised names (case and repeated whitespace ignored), phone numbers with ASCII spaces removed (keeping a leading + significant), email local parts exactly with domains compared without regard to ASCII case, and trimmed addresses exactly. Tags and the edited record are ignored. Preserve stored spelling. JSON loading keeps the legacy exact-contact rule; tag-only and unchanged-contact edits remain possible on legacy variants. See contact identity.
  3. Tags: store each tag once per member, match without regard to case, retain its spelling and display tags in ASCII order. See the User Guide for tag syntax and length limits.
  4. Listing and search: list clears conditions while preserving stored order. find adds a partial-name condition; findemail also narrows the displayed list with a literal email search. Keywords within one search use OR; successive conditions use AND. Repeating a search reports that it is already active, and a different query with unchanged results reports Results unchanged. Searches retain stored order.
  5. Tag filtering: each filter adds one OR group of tags; separate groups combine with AND. Repeating the same complete tag set, ignoring letter case, order and repetition, reports an already-active filter without changing conditions. Zero matches is a valid result.
  6. Displayed indexes: indexed commands use the current filtered display in stored order, numbered from 1. Accept ASCII positive integers and leading zeroes; reject signs, decimals, internal spaces and out-of-range values. A view change can renumber members.
  7. Individual updates: edit changes supplied fields only; supplied tags replace the entire tag set. Bare a/ clears an address and bare t/ clears tags. tag/untag change one assignment. Re-evaluate conditions after updates, so a changed member can leave the view without being deleted.
  8. Bulk tag updates: snapshot displayed targets; preserve hidden members and unrelated tags. Skip redundant assignments and count against the snapshot. Reject an empty target set or a rename with no matching old tag. Case-only renames skip members already using the requested spelling.
  9. Save policy: sort and executed record-changing commands save the complete roster, including valid no-ops. View commands, help, export, exit, and confirmation prompts/cancellations do not save the JSON roster.
  10. Save failures: report success only after saving; a failed write preserves the previous roster file. Failed clear restores records and the prior view; retry with clear after fixing storage. Other applied changes remain in memory and can be lost on exit; retry saving with a valid no-op. See saving and recovery for backup rollback and retry details.
  11. Add and destructive actions: add appends a record and clears conditions. Delete retains conditions; clear removes displayed records while keeping hidden members and conditions; clear /all removes everyone and resets conditions. Non-empty delete/clear requests require the next input to be exactly yes, to prevent accidental deletion. A near miss such as y keeps the prompt pending; any other reply cancels and is consumed. Neither action has undo. An empty roster still saves immediately. Clear accepts only an optional /all; list, sort and exit reject extra arguments.
  12. Startup and exit: load the packaged JAR's data/addressbook.json; missing data loads samples, while a valid empty roster stays empty. Invalid data requires preservation and recovery before editing. Normal startup, read-only commands and exit do not save the roster.
  13. Feedback: input errors explain correction or direct the user to help; duplicate errors reject rather than merge records. Storage errors identify unsaved changes using rule 10.

Command and field reference

The User Guide specifies command syntax, field constraints and offline help. Implementation details belong in command parsing, member details and offline help.

Unicode address edits: EditCommandParser preserves Unicode whitespace in supplied field values until validation. An a/ containing only Unicode whitespace, including U+2003 (EM SPACE), is rejected; only an empty a/ intentionally clears an address. The Unicode input regression tests cover this distinction.

  3. NFR03: Offline use: core commands and help work with networking disabled. No team-operated server is required.
  4. NFR04: Keyboard access: complete every in-app operation using commands and keyboard navigation. Manual file editing uses an external editor.
  5. NFR05: Display: keep controls and text readable, without overlap, at:
    • 1920 × 1080 or higher with 100% and 125% scaling.
    • 1280 × 720 or higher with 150% scaling.
    • Long lists and help text remain reachable through scrolling.
  6. NFR06: Privacy: core operations do not transmit contacts to external services. Local files rely on OS access controls; the app provides no login or encryption.
  7. NFR07: Storage: use local, human-editable UTF-8 JSON without a DBMS. Support corrections in a text editor while the app is closed.
  8. NFR08: Response time: complete each valid command within two seconds under this test workload:
    • 500 members; writable data file up to 1 MB; command up to 256 characters.
    • 2 GHz dual-core CPU, 4 GB RAM and local SSD, without competing heavy work.
    • Measure submission to visible result, including saving. Exclude startup and shutdown.
    • Record OS, Java version, hardware, dataset and timings. These are test conditions, not input limits.
  9. NFR09: Reliability: retain successfully saved data after restart.
    • A write failure preserves the previous roster and never reports success.
    • Apply the in-memory failure policy in shared rule 10, including clear rollback.
    • Exit closes without a separate roster save.

Validation, duplicates and filters are functional rules. Development-process rules are not product NFRs.

Glossary

Term Meaning
Active condition A removable name, email, tag or index-selection restriction on the displayed list. All active conditions must match for a member to be displayed.
Backup The .bak copy of the previous distinct saved roster. It contains one earlier version, not a complete history.
Bulk tag update A tag change applied to the members displayed when the command is submitted.
CSV Comma-separated values: a text format that represents a table as rows of fields. TrackCall uses CSV to import and export rosters for use with spreadsheets and other tools.
Data-changing command A command intended to modify roster records, including a valid request that makes no change.
Displayed list The members visible after applying the current conditions to stored order. Displayed indexes refer to this view.
Duplicate record A contact whose normalised name and trimmed phone, email and address match another record; tags do not distinguish contacts. See contact identity for the separate JSON-loading rule.
Group Members sharing a tag, such as a committee or cohort. A group is not a separate stored object.
In-memory data The working roster held by the running app, which can differ from the saved file after a save failure.
Index A member's position in the displayed list, starting at 1. It can change when the view changes.
JAR Java Archive: the packaged application file, launched with java -jar.
JSON JavaScript Object Notation: a structured text format using objects, arrays and values. TrackCall uses JSON for its local roster and preferences files.
No-op A valid operation that leaves record values unchanged.
Partial-word matching Matching a contiguous part of a name word without regard to case; for example, oh matches John Tan.
Persisted data The roster successfully written to disk and available after restarting the app.
Read-only command A command that leaves roster records and the automatic JSON roster file unchanged. It may change the view or write a separate export file.
Roster / address book The complete collection of member records, including hidden members. The starter code uses the name address book.
Tag A case-insensitive label assigned to a member to represent group membership. Its original spelling is retained for display.

Appendix: Instructions for Manual Testing

Use a disposable folder and synthetic contacts. These are starting points, not a complete test plan: vary the inputs freely, and see the User Guide for each command's full rules. Record the release version, Java version, OS and actual result for each run.

Test setup

  1. Put the supplied TrackCall JAR in a new, writable folder. Run java -version to confirm Java 25, then launch with java -jar "trackcall.jar" from that folder in a terminal.
  2. Before each independent scenario below, and wherever a step says "Restore the fixture", recreate this fixture by entering each command separately:
clear /all
yes
add n/Zara Lim p/90000001 e/zara@example.com a/Test Road t/friends
add n/Bob Lee p/90000002 e/bob@school.edu t/committee
add n/Alice Tan p/90000003 e/alice@example.com a/Main Street t/committee

Expected baseline: three members in stored order: Zara, Bob, Alice. Bob has no address. Enter yes only when clear /all prompts for confirmation; an already-empty roster needs no answer. Use list and check the displayed indices before any indexed command. Back up test files before fault injection.

Launch and shutdown

  1. Start in a new folder without a roster file. Expect: sample members and a usable command box.
  2. Run list extra, clear extra, and exit extra. Expect: input errors, unchanged records, and an open app. Run exit, then restart. Expect: the last successfully saved roster.
  3. Launch the same JAR twice. Expect: the second process reports that the app is already running. Close the first and relaunch. Expect: startup succeeds without deleting .trackcall.lock.
  4. Move and resize the window, close, and restart. Expect: valid saved bounds are restored. Repeat after disconnecting its former display. Expect: the window remains reachable.

Offline help and member details

Setup: restore the fixture and disable networking.

  1. Open help, F1, and the Help menu. Expect: the same offline overview of all 19 commands. Open help edit and the overview's edit button. Expect: matching syntax, examples and errors. Use arrow keys, Page Up/Down, Home/End, and Escape. Expect: reachable content and a closing window.
  2. Try help ADD, help unknown, and help add edit. Expect: errors without record or view changes.
  3. Press F2 and select a member with arrow keys. Expect: that member's complete contact details. Select Bob. Expect: the absent-address copy control is disabled. Press Escape. Expect: hidden details and focus in the command box.
  4. Add, edit, untag, and confirm a delete. Expect: the details panel clears and the feedback shows the name and sorted tags but no phone, email, or address.

Add, edit and validation

  1. Add a fourth member without a/. Expect: an absent address that survives restart. Run edit 1 a/. Expect: Zara's address is cleared. Run edit 1 t/committee t/year1, then edit 1 t/. Expect: replaced tags, then no tags.
  2. Try, separately, a missing required field, repeated n/, invalid phone/email, empty add ... a/, edit 1, and appending x/extra or T/committee. Expect: rejection without changes.
  3. Add Alice's contact details with different tags, then repeat using alice tan and Alice Tan. Expect: duplicate rejection each time. Change the phone and retry. Expect: a separate record.
  4. Add n/Chloé O'Connor p/+65 9123 4567 e/chloe.o'connor@example.com a/Block A/12 t/year-1. Expect: accepted with spelling preserved. Also check Ravi s/o Kumar and J. Tan as names. Then try one invalid value at a time: n/-Anne, n/Alice@Other, p/1 2, p/65+, e/john..doe@example.com, and a/ followed only by a nonbreaking space (U+00A0). Expect: a field-specific error each time, with no record added.

Search, filter and selection

  1. Run list, then find ali. Expect: Alice. Run find Zara Bob. Expect: no matches, with two Name boxes: a member must satisfy both searches. Remove Name: ali. Expect: Zara and Bob; the other search remains. After list, run find Zara Bob alone. Expect: Zara and Bob (OR within one search).
  2. Run list, filter t/committee, then find Alice. Expect: Alice only. Remove the name box. Expect: Bob and Alice. Run filter t/COMMITTEE. Expect: one tag box and an "already active" message.
  3. Run list, then filter t/committee t/friends. Expect: all three members and one Tag box. Run filter t/committee. Expect: Bob and Alice with a second Tag box, because a single tag is a different condition from the OR group. Remove it. Expect: all three members; the OR group remains.
  4. Run list, show 1 3, then show 2. Expect: Zara and Alice, then Alice only, with chips Show: 2 selected and Show: 1 selected. Repeat show 1. Expect: no extra chip. Hover over the remaining chip. Expect: names in alphabetical order.
  5. Run list, sort, filter t/committee, then findemail @EXAMPLE.COM. Expect: Alice only, with boxes Tag: committee and Email: @EXAMPLE.COM. Run findemail alice. Expect: Results unchanged. and a third box. Run findemail ALICE alice. Expect: an "already active" message and still three boxes.
  6. Run list, then findemail alice@example.com @school.edu. Expect: Alice and Bob (OR matching). Run list, then findemail .*. Expect: zero matches, not regular-expression matching.
  7. Edit Alice's email to alice@other.net while an @example.com email search is active. Expect: Alice leaves the view but remains stored; list shows all three.
  8. Try find or findemail without a keyword, an empty tag filter, and an out-of-range show. Expect: errors preserving the preceding view.

Individual and bulk tags

  1. Run tag 1 t/year1 twice. Expect: Zara gains one tag; repetition reports no change. Run list, filter t/committee, then tagall t/year1 twice. Expect: Bob and Alice gain the tag; the second command skips both.
  2. Run untagall t/committee. Expect: both members leave the filtered view. Run list. Expect: all three remain stored with their other tags intact.
  3. Run find Alice, then renametag t/year1 t/alumni, followed by list. Expect: only Alice's tag is renamed; hidden members retain year1.
  4. Restore the fixture. Run filter t/committee, then untag 1 t/committee. Expect: Bob disappears from the view but remains in the roster.
  5. Restore the fixture again, because step 4 removed Bob's only tag. Run filter t/committee, then renametag t/committee t/Committee. Expect: two changed members, both still displayed. Run renametag t/committee t/Committee again. Expect: zero changed. Run renametag t/committee t/alumni. Expect: both members leave the old-tag filter; removing it returns all three, with alumni on Bob and Alice.
  6. Try invalid indices, empty tags, two tags for tagall, identical old/new tags for renametag, a bulk update on an empty view, and each tag command with n/extra or a/Home. Expect: format or usage errors without changes.

Delete and clear

  1. Run find Alice, then delete 1. Expect: a confirmation naming Alice; no deletion yet. Enter list. Expect: cancellation; list is consumed and the message says it was not run. Repeat delete 1, then enter no. Expect: only the plain cancellation message.
  2. Run delete 1, then y, Y and YES in turn. Expect: each keeps the prompt pending with a reminder to type yes exactly, and nothing is deleted. Enter yes. Expect: Alice is deleted.
  3. Try delete 0, delete -1, a very large integer, and an index beyond the displayed list. Expect: errors without deletion.
  4. Restore the fixture, run filter t/committee, clear, then yes. Expect: only committee members removed, with the filter still applied; list reveals Zara. With an empty result and hidden records, expect clear to neither prompt nor save, while clear /all still prompts for everyone.
  5. Restore the fixture, run find Alice, then clear /all. Expect: a prompt counting all three records. Enter y, then yes. Expect: the prompt stays pending, then everyone is removed, including hidden members.
  6. Run clear on the empty roster. Expect: the already-empty message after saving, without confirmation. .bak still holds the previous distinct roster. A confirmed clear has no undo.

Sorting and CSV

Setup: restore the fixture. Use only files inside the disposable application folder.

  1. Run filter t/committee, then sort. Expect: Alice and Bob displayed, while all three stored members are ordered Alice, Bob, Zara. Run list and restart: that order persists. Try sort date. Expect: an error preserving the view and saved bytes. Add a member whose name precedes Alice, and import another new member. Expect: both append at the end rather than inserting alphabetically.

  2. Run filter t/committee, sort, then export members.csv. Expect: Alice and Bob exported in displayed order, hidden Zara excluded and counted, and the view unchanged. Inspect the CSV. Expect: a UTF-8 header, quoted fields where needed, and sorted semicolon-separated tags.

  3. Run import p/members.csv. Expect: zero imports and two skipped duplicates; filters reset. Run clear /all, confirm with yes, then import again. Expect: two imports that persist after restart.

  4. Copy the CSV to member list.csv. Expect: import p/"member list.csv" works, and export member list.csv without quotes creates a file named exactly that. Try each malformed import separately. Expect: an error naming the problem, with no change to the roster, view or saved file.

    • import p/"member list.csv (unmatched quote) and import p/member list.csv (unquoted whitespace).
    • import p/a.csv p/b.csv (repeated p/), import x/a.csv (unknown prefix) and import p/"" (empty path).

  5. Import this CSV. Expect: a row-specific error with no partial import, save, or view change.

    name,phone,email,address,tags
New Member,90000004,new@example.com,,committee
Invalid Member,12,invalid@example.com,,committee

  6. Try export "members.csv", export members.txt, and export folder.csv where folder.csv is a directory. Export to a missing directory, a protected application file, and a path outside the application folder. Expect: handled errors with extension or folder guidance, and no file replaced.

  7. Import a file over 10 MiB, then a separate file with 10,001 valid nonblank member rows. Expect: the matching limit error with no imports, saves or view changes.

  8. In a separate disposable roster, add several members with the same name and distinct phone numbers. Run sort, then tagall t/year1 and a phone-only edit. Expect: tied names retain stored roster order after each.

  9. Apply name, tag and Show conditions, then sort. Expect: the same conditions and selected members, displayed in stored name order. Sort an empty roster: it saves successfully.

Persistence and invalid files

Use a fresh fixture and backup for each failure scenario. Restore access before exiting the app.

  1. Save a change, restart the packaged JAR from a different working directory, and check the roster. Expect: the same application-folder data and complete fields and tags.
  2. With the app closed, replace the roster with malformed JSON, null, a null member, or a null tag, each separately. Expect: a recovery dialog stating the load failure and an exact-byte, uniquely named recovery copy. Try Close, Restore backup, and Start empty. Expect: Close preserves the invalid file; recovery preserves the damaged copy and existing backup.
  3. Test null preferences and null guiSettings. Expect: usable defaults. In a valid JSON roster, keep two names differing only in case with identical other fields. Expect: both load, and tag-only edits remain possible.
  4. While the app is open, remove write permission from its data directory but keep read access (on Windows, deny write access). Making only addressbook.json read-only may still allow atomic replacement, so first confirm a save error occurs. Test add, edit, tag, untag, confirmed delete, tagall, untagall, renametag, import, and sort independently.
    • Expect: a save error with retry guidance; the change stays in memory and saved bytes are unchanged. Pressing Enter again must not repeat the command.
    • Restore access, reapply an existing field with edit, then restart. Expect: the current roster is saved.
  5. Repeat the write failure with clear while a filter hides members, confirming with yes. Expect: no members removed, the full roster and previous filtered view restored, and unchanged saved bytes. Restore access, run clear again, and confirm. Expect: only displayed targets removed.
  6. With the app closed, add surrounding whitespace to valid JSON contact and tag fields and a leading UTF-8 byte-order mark, then restart. Expect: loading succeeds with outer whitespace trimmed. Test a whitespace-only address separately. Expect: a recovery dialog, not an empty address.
  7. While the app is open, replace the data file with a different valid roster, then attempt a data change. Expect: the first save is refused with outside-edit guidance and the file is preserved. Restart to load the outside version, or retry with an existing field value. Expect on retry: the outside version is backed up in .bak.
  8. Rename a tag by capitalization only. Expect: .bak retains the previous spelling.

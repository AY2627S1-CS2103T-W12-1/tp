Testing guide

Running tests

You can run tests in two ways.

Use Java 25. build.gradle explicitly enables Java assertions for tests and Java execution tasks, including run and runShadow. Generated launch scripts also use -ea through applicationDefaultJvmArgs. For a direct packaged run, use java -ea -jar trackcall.jar. In an IntelliJ Application run configuration, add -ea to the VM options.

  • Method 1: Using IntelliJ JUnit test runner
    • To run all tests, right-click on the src/test/java folder and choose Run 'All Tests'
    • To run a subset of tests, you can right-click on a test package, test class, or a test and choose Run 'ABC'
  • Method 2: Using Gradle
    • Open a console and run the command gradlew clean test (Mac/Linux: ./gradlew clean test)
:link: **Link**: Read [this Gradle Tutorial from the se-edu/guides](https://se-education.org/guides/tutorials/gradle.html) to learn more about using Gradle.

Types of tests

The automated suite includes these types of tests:

  1. Unit tests target the lowest-level methods and classes.
    For example: seedu.address.commons.util.StringUtilTest

  2. Integration tests check how multiple code units work together; the individual units are assumed to work.
    For example: seedu.address.storage.StorageManagerTest

  3. Hybrid tests combine unit and integration testing. These tests check both the individual units and how they work together.
    For example: seedu.address.logic.LogicManagerTest

  4. UI tests exercise JavaFX controls and their interaction with logic and storage.
    For example: seedu.address.ui.MainWindowTest checks command feedback, selection, and persisted changes.

Randomised CSV and recovery checks

Expected results come from the User Guide and user stories, rather than from observed implementation behaviour. UserCsvWorkflowTest exercises typed commands, real CSV fixtures, saved files, and fresh storage sessions. It covers sharing the whole roster while searching, restoring exported data, hidden duplicates, documented field boundaries, rejected imports preserving the view and files, and retrying an unsaved batch. Its CSV expectations are written independently of the exporter, and its feedback expectations do not use production message constants. A failure against a documented promise must be investigated as a possible bug; do not weaken an expectation just to make the test pass.

The initial cross-check against team master 6a04ef41 exposed missing address clearing, overwritten distinct backups after unchanged saves or repeated clears, and missing import-save recovery guidance. PR #212, merged in 58b44653, addresses these differences. The acceptance tests retain the documented expectations as regression coverage, including unchanged-save backup preservation across recovery cycles.

The larger generated datasets are additional robustness checks. Their sizes are test inputs, not new product limits or performance guarantees. CSV syntax and UTF-8 validity also determine whether an input should be rejected.

The normal test suite includes generated CSV round trips and storage failure scenarios. Run just these checks with:

./gradlew test --tests '*CsvRoundTripRandomizedTest' --tests '*RosterRecoveryRandomizedTest'

Run the user workflow acceptance scenarios with ./gradlew test --tests '*UserCsvWorkflowTest'.

Run the independent command-sequence oracle with ./gradlew test --tests '*CommandSequenceOracleTest'. It generates 3,200 reproducible workflow steps across eight seeds, comparing a plain-record reference roster with the application after each step. It checks stored order, displayed members, filters, show selections, CSV re-import, deletion confirmation/cancellation, tag changes, tag renaming, and process-session reloads. Read-only steps must also preserve the saved file's exact bytes. A separate failure-injection scenario checks that a failed clear restores a composed search/tag/show/sort view and that a later bulk tag command updates only its intended member. Filter-removal actions call the same model/logic methods as the UI; this oracle does not simulate native mouse clicks, window sizing, or keyboard focus.

On Windows PowerShell, use .\gradlew.bat instead of ./gradlew. Gradle may reuse a previous result; add --rerun-tasks to force a fresh run.

  • CSV checks use 40 fixed seeds, including empty and 500-member rosters, and repeat each round trip three times. Generated fields include quotes, commas, tabs, Unicode, empty addresses, leading-zero phones, and mixed-case tags. Another 20 seeds check that an encoding failure after valid rows preserves the previous export and removes temporary files. Extreme cases include a 5,000-member roster, fields of over 10,000 characters, 2,000 tags on one member, and 60 shuffled-column fixtures with quoted values, BOMs, blank rows, and different line endings. Invalid final rows after 1,000 valid members must leave the existing model unchanged. Malformed UTF-8, an unclosed field containing 100,000 escaped quote characters, and 10,000 blank rows check encoding rejection, syntax handling, and physical error-row reporting.
  • Recovery checks use 30 fixed seeds to truncate saved rosters at different positions, reject unsafe saves, preserve damaged bytes, restore the previous backup, and verify saving resumes after recovery. A separate check blocks backup replacement with a non-empty directory, repairs it, and retries the save. Further cases truncate a Unicode roster at every byte offset, run 20 corruption/recovery cycles while checking every preserved copy and unchanged-save backup preservation, reject same-length changes during recovery, handle invalid backups, and reject JSON nested 2,000 levels deep without overwriting the backup.

Failures report the seed and, for round trips, the iteration. All files live in JUnit temporary directories; these checks do not use your real roster. They run automatically in the existing CI test jobs on Windows, macOS, and Linux. They simulate specific write and corruption failures; they do not simulate a full disk or a power outage.

Release verification

Run ./gradlew check shadowJar with Java 25 to check code style, run the automated suite, and build build/libs/trackcall.jar. Run npm ci and npm run build from docs/ to verify the production website. Tests and the documentation build passing are necessary checks; also exercise the packaged JAR and rendered guides.

Use the manual test instructions for the complete membership workflows, invalid inputs, persistence, and recovery scenarios. Start with a temporary, writable folder and synthetic members so destructive commands cannot remove real data. Check the User Guide's examples against the same JAR intended for release, including filtered member numbers and CSV round trips.

Record the source revision, Java version, operating system, JAR checksum, and completed scenarios with the release. Repeat the relevant regression checks after a fix and the full release checks after integration. The website's navigation, images, tables, and section links should also be inspected at desktop and phone widths.

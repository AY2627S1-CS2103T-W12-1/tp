## Build automation

Gradle manages builds and dependencies.
See the [Gradle tutorial](https://se-education.org/guides/tutorials/gradle.html) for background.

Use Java **25** for every build and test task.
On macOS with SDKMAN, select it with `sdk use java 25.0.3.fx-zulu` when needed.

Run these commands from the repository root.
On Windows, replace `./gradlew` with `gradlew.bat`.

| Command | Purpose |
| --- | --- |
| `./gradlew clean` | Remove files generated by earlier build tasks. |
| `./gradlew shadowJar` | Create the fat JAR at `build/libs/addressbook.jar`. |
| `./gradlew run` | Build and run the application. |
| `./gradlew runShadow` | Build and run the fat JAR. |
| `./gradlew checkstyleMain` | Check the main source code's style. |
| `./gradlew checkstyleTest` | Check the test source code's style. |
| `./gradlew test` | Run all tests. |
| `./gradlew clean test` | Clean the project, then run all tests. |

### Apple Silicon development and release testing

On an ARM macOS JVM, `run` and `test` select the matching JavaFX native libraries.
These local dependencies are separate from `shadowJar`.
Intel and ARM macOS libraries have colliding filenames, so they cannot share the same fat JAR unchanged.

For packaged launches on Apple Silicon, use the course-compatible JDK+FX distribution.
Passing `run` or `test` does not verify the release JAR.
Test the actual JAR on Windows, macOS, and Linux before declaring it portable.

## Continuous integration (CI)

GitHub Actions runs the workflows in `.github/workflows`. No further setup is required.

### Code coverage

Gradle generates JaCoCo coverage reports from the tests. CI uploads the coverage data to Codecov.
Coverage uploads can fail independently of the application tests.
Check the coverage report periodically, even when CI passes.

For a fork, follow the [Codecov setup guide](https://se-education.org/guides/tutorials/codecov.html).

### Repository-wide checks

CI also checks repository files outside the Gradle build, including line endings.
These checks use POSIX shell scripts and run locally on macOS or Linux.

From the repository root, run:

```shell
./.github/run-checks.sh
```

Warnings and errors appear in the console.

#### Add a check

1. Create an executable `check-*` script in `.github`.
   `run-checks.sh` discovers it automatically.
2. Report problems as `SEVERITY:FILENAME:LINE: MESSAGE`.
3. Exit with a non-zero code if any errors occur.

| Part | Meaning |
| --- | --- |
| `SEVERITY` | `ERROR` or `WARN`. |
| `FILENAME` | File path relative to the current directory. |
| `LINE` | Line where the problem occurs. |
| `MESSAGE` | Explanation of the problem. |

## Making a release

The v1.1 documentation iteration and v1.2 first increment do not require a release.
The current version, `v1.2-dev`, is a development build rather than a published release.

For an iteration that requires a release:

1. Update the version in
   [`MainApp.java`](https://github.com/AY2627S1-CS2103T-W12-1/tp/tree/master/src/main/java/seedu/address/MainApp.java).
2. Run automated tests and code checks with Java 25.
3. Run `./gradlew shadowJar` to generate the fat JAR.
4. Complete the [release acceptance checks](DeveloperGuide.md#release-acceptance-checks-still-required) on that JAR.
5. Create a lightweight tag for the release commit using the agreed version, such as `v1.3`.
6. [Create a GitHub release](https://help.github.com/articles/creating-releases/) and upload the JAR.

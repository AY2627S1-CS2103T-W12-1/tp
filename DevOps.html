DevOps guide

Build automation

This project uses Gradle for build automation and dependency management. We recommend reading this Gradle tutorial from se-edu/guides.

The following commands perform common Gradle tasks.

  • clean: Deletes the files created during the previous build tasks (e.g. files in the build folder).
    For example: ./gradlew clean

  • shadowJar: Uses the Shadow plugin to create the fat JAR file build/libs/trackcall.jar.
    For example: ./gradlew shadowJar

  • run: Builds and runs the application.
    runShadow: Builds the application as a fat JAR, then runs it.

  • checkstyleMain: Runs the code style check for the main code base.
    checkstyleTest: Runs the code style check for the test code base.

  • test

    • ./gradlew test: Runs all tests.
    • ./gradlew clean test: Cleans the project before running all tests

Local runs and release verification

Use Java 25 for build tasks and application runs. On Apple Silicon, Gradle selects the ARM JavaFX libraries for run and test. The portable shadowJar bundles both macOS architectures in separate folders, and Main selects the matching native libraries at startup. Windows and Linux use their bundled JavaFX libraries.

A passing local Gradle run does not verify the packaged release. Build with ./gradlew shadowJar, copy build/libs/trackcall.jar into an empty writable folder, and run java -jar trackcall.jar using Java 25. Repeat the release smoke test on Windows, Linux, and macOS, including startup, commands, saving, and restart. Use synthetic contacts and follow the manual testing instructions.

Continuous integration (CI)

Documentation dependencies

In docs, run npm ci, npm test, and npm run build to install the locked dependencies, check compatibility, and verify the generated site. npm audit checks the installed dependency tree.

MarkBind 7.2.1 still requests older libraries with known vulnerabilities. package.json overrides select patched releases, and patch-package applies the small API adaptations in docs/patches during installation. These retain MarkBind's existing Cheerio and HTML parser behavior. The lodash.pick dependency is an alias for maintained Lodash; the Cheerio patch selects its pick function. Keep the overrides and patches together, and review them when upgrading MarkBind. Do not skip install scripts: the unpatched APIs are incompatible. CI runs the compatibility tests and builds every page.

This project uses GitHub Actions for CI. The necessary workflow configuration files are in .github/workflows. No further setup is required.

Code coverage

As part of CI, Gradle generates JaCoCo coverage reports from the tests, and CI uploads the coverage data to Codecov. Codecov then provides information about test coverage.

CI uploads coverage from pushes to master, from pull requests branched inside the team repository (authenticated with the workflow's OIDC token), and from pull requests made from member forks (using Codecov's tokenless upload for forks of public repositories, since GitHub gives those runs no token). A failed upload is reported without failing the build, so developers are advised to check the code coverage levels periodically on Codecov and take corrective actions if the coverage level falls below desired levels.

To enable Codecov for forks of this project, follow the steps given in this se-edu guide.

Repository-wide checks

In addition to Gradle checks, CI runs repository-wide checks. Unlike Gradle checks, which cover files used in the build, these checks cover every repository file and enforce rules that are hard to apply on development machines, such as line-ending requirements.

These checks are implemented as POSIX shell scripts, and thus can only be run on POSIX-compliant operating systems such as macOS and Linux. To run all checks locally on these operating systems, execute the following in the repository root directory:

./.github/run-checks.sh

Any warnings or errors will be printed out to the console.

If adding new checks:

  • Checks are implemented as executable check-* scripts within the .github directory. The run-checks.sh script will automatically pick up and run files named as such. That is, you can add more such files if you need and the CI will do the rest.

  • Check scripts should print out errors in the format SEVERITY:FILENAME:LINE: MESSAGE

    • SEVERITY is either ERROR or WARN.
    • FILENAME is the path to the file relative to the current directory.
    • LINE is the line of the file where the error occurred and MESSAGE is the message explaining the error.

  • Check scripts must exit with a non-zero exit code if any errors occur.

Making a release

Here are the steps to create a new release.

  1. Update the version number in MainApp.java.
  2. Generate a fat JAR file using Gradle (i.e., ./gradlew shadowJar).
  3. Tag the repo with the version number. e.g. v0.1
  4. Create a new release using GitHub. Upload the JAR file you created.
